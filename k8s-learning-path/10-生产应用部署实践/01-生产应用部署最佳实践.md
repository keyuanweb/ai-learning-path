# 生产应用部署最佳实践

## 目标

以部署一个典型的 Web 服务为例，完整展示生产级 K8s 应用需要配置的每一项——从 Pod 安全上下文到 HPA 弹性伸缩，从健康检查到 PodDisruptionBudget。每个配置点都标注了「为什么需要」，而非单纯罗列 YAML。

> **类比**：在 kind 上 `kubectl create deployment nginx --image=nginx` 是过家家——5 秒部署，能跑就行。生产环境部署是做手术，每个环节（入口消毒、资源配给、健康监控、滚动更新）都缺一不可。

## 示例应用：假想的 API 网关

以下所有 YAML 以一个 Go 编写的 API 网关为例：

```
镜像:    registry.internal/my-api-gateway:v2.5.0
端口:    8080（HTTP API）+ 9090（metrics / Prometheus）
资源:    正常运行时 CPU ~200m、内存 ~256Mi
副本:    日常 3，高峰期可扩到 10
域名:    api.internal.example.com
```

## 1. Namespace 与 RBAC

把不同应用/环境放在独立 namespace，配合 RBAC 做权限隔离。

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: api-gateway-prod
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: api-gateway
  namespace: api-gateway-prod
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: api-gateway
  namespace: api-gateway-prod
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list", "watch"]        # 只读 ConfigMap，不碰 Secret
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: api-gateway
  namespace: api-gateway-prod
subjects:
  - kind: ServiceAccount
    name: api-gateway
    namespace: api-gateway-prod
roleRef:
  kind: Role
  name: api-gateway
  apiGroup: rbac.authorization.k8s.io
```

> **为什么**：避免 `default` namespace 混放 50 个应用导致 `kubectl get all` 变成灾难。每个应用最小权限 SA，不挂载 `cluster-admin`。

## 2. ConfigMap 与 Secret

将配置和敏感数据外置，后面通过 Volume 或 envFrom 注入 Pod。

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-gateway-config
  namespace: api-gateway-prod
data:
  config.yaml: |
    server:
      port: 8080
      read_timeout: 5s
      write_timeout: 10s
    upstream:
      endpoint: "http://backend-service.backend-prod.svc.cluster.local:9090"
      max_retries: 3
---
apiVersion: v1
kind: Secret
metadata:
  name: api-gateway-secret
  namespace: api-gateway-prod
type: Opaque
stringData:
  JWT_SECRET: "prod-jwt-signing-key-change-me"
  DB_PASSWORD: "R3@p1ac3W!thR3@lP@ss"
```

> **注意**：生产环境 Secret 的敏感数据不应明文写在 YAML 里提交 Git。实际用 External Secrets Operator（ESO）对接 Vault/AWS Secrets Manager，或至少用 Sealed Secrets 加密后入库。

## 3. Deployment 完整配置

核心部署对象，把所有最佳实践串在一起。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-gateway
  namespace: api-gateway-prod
  labels:
    app: api-gateway
    version: v2.5.0
spec:
  replicas: 3
  revisionHistoryLimit: 5           # 仅保留最近 5 个 ReplicaSet，方便回滚
  minReadySeconds: 10               # Pod Ready 后等 10s 再标记为 Available
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                   # 滚动更新时最多多出 1 个 Pod
      maxUnavailable: 1             # 最多 1 个 Pod 不可用

  selector:
    matchLabels:
      app: api-gateway

  template:
    metadata:
      labels:
        app: api-gateway
        version: v2.5.0
      annotations:
        prometheus.io/scrape: "true"       # Prometheus 自动发现
        prometheus.io/port: "9090"
        prometheus.io/path: "/metrics"
        checksum/config: ""                # 部署时手动填入 ConfigMap hash 触发滚动更新

    spec:
      serviceAccountName: api-gateway
      terminationGracePeriodSeconds: 30    # 优雅停止宽限期

      # —— 镜像拉取 ——
      imagePullSecrets:
        - name: registry-internal-creds

      # —— 安全上下文（Pod 级别） ——
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        runAsGroup: 3000
        fsGroup: 3000

      # —— 调度约束 ——
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:   # 软反亲和
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchLabels:
                    app: api-gateway
                topologyKey: kubernetes.io/hostname          # 尽量分散到不同节点
      nodeSelector:
        workload: app                                        # 只调度到标记了该 label 的节点

      # —— 容忍度（可选） ——
      tolerations:
        - key: "app"
          operator: "Equal"
          value: "true"
          effect: "NoSchedule"

      containers:
        - name: api-gateway
          image: registry.internal/my-api-gateway:v2.5.0
          imagePullPolicy: IfNotPresent          # 生产建议 IfNotPresent，减少 registry 压力

          ports:
            - name: http
              containerPort: 8080
              protocol: TCP
            - name: metrics
              containerPort: 9090
              protocol: TCP

          # —— 环境变量 ——
          env:
            - name: CONFIG_PATH
              value: /etc/api-gateway/config.yaml
            - name: GOMEMLIMIT
              valueFrom:
                resourceFieldRef:               # 将 memory limit 暴露给应用，Go 1.19+ 自动调 GC
                  resource: limits.memory
          envFrom:
            - secretRef:
                name: api-gateway-secret         # JWT_SECRET、DB_PASSWORD

          # —— 资源限制 ——
          resources:
            requests:
              cpu: 200m
              memory: 256Mi
            limits:
              cpu: 1000m
              memory: 512Mi

          # —— 探针 ——
          startupProbe:                          # 对于需要预热的应用，先检查 startup
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 5
            failureThreshold: 30                 # 最多等 5 + 30*5 = 155s
            periodSeconds: 5

          livenessProbe:                         # 进程"活着"检查——死锁、hang 住的情况
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 0               # startupProbe 通过后立即开始
            periodSeconds: 15
            timeoutSeconds: 3
            failureThreshold: 3                  # 3 次失败 → 重启

          readinessProbe:                        # 是否"能接流量"——依赖就绪检查
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 3                  # 3 次失败 → 从 Service 摘除
            successThreshold: 1

          # —— 容器安全上下文 ——
          securityContext:
            readOnlyRootFilesystem: true         # 根文件系统只读
            allowPrivilegeEscalation: false
            capabilities:
              drop:
                - ALL                            # 丢弃所有 Linux capabilities

          # —— 卷挂载 ——
          volumeMounts:
            - name: config
              mountPath: /etc/api-gateway
              readOnly: true
            - name: tmp
              mountPath: /tmp                    # 只读根文件系统下，/tmp 需要可写

      volumes:
        - name: config
          configMap:
            name: api-gateway-config
        - name: tmp
          emptyDir: {}                           # Pod 内临时存储，Pod 删除即清空
```

### 各配置项的设计意图

| 配置 | 为什么需要 |
|---|---|
| `runAsNonRoot: true` | 降低容器逃逸风险——哪怕应用有漏洞，攻击者也只能以非 root 操作 |
| `readOnlyRootFilesystem: true` | 防写后门/挖矿程序，应用只能写入显式挂载的 `/tmp` |
| `drop: [ALL]` | 减少攻击面——容器不需要 `NET_ADMIN`、`SYS_ADMIN` 等特权 |
| `podAntiAffinity` (软) | 尽量分散 Pod 到不同节点，一个节点宕机不导致所有副本下线 |
| `nodeSelector` | 专用节点池隔离——不和数据库/日志服务抢资源 |
| `startupProbe` | 保护慢启动应用——在启动完成前不触发 liveness 导致循环自杀 |
| `readinessProbe` | 滚动更新/扩容时，Pod 准备就绪才加入 Service 接收流量 |
| `livenessProbe` | 自动恢复卡死的进程——死锁、OOM、死循环 |
| `GOMEMLIMIT` + `resourceFieldRef` | Go 程序根据容器 limit 而非宿主机内存调 GC，避免 OOMKilled |
| `minReadySeconds: 10` | 给控制器一点时间观测 Pod 真实状态，避免刚 Ready 就切流量 |
| `terminationGracePeriodSeconds: 30` | 优雅停止——给应用充足时间 drain 连接、持久化状态 |

## 4. Service 暴露

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api-gateway
  namespace: api-gateway-prod
  labels:
    app: api-gateway
spec:
  type: ClusterIP
  sessionAffinity: None
  ports:
    - name: http
      port: 80
      targetPort: http      # 用命名端口而非端口号，更清晰
      protocol: TCP
  selector:
    app: api-gateway
```

## 5. PodDisruptionBudget

保护服务在**自愿性中断**（节点维护、集群升级）时保有最小可用副本数。

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-gateway-pdb
  namespace: api-gateway-prod
spec:
  minAvailable: 2           # 任何时候至少 2 个 Pod 可用
  selector:
    matchLabels:
      app: api-gateway
```

> **效果**：假设 3 副本，`minAvailable: 2` 意味着 `kubectl drain` 时如果 2 个 Pod 在同一节点上，drain 命令会阻塞等待 Pod 重新分布，不会同时驱逐导致服务中断。

## 6. HPA 弹性伸缩

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-gateway-hpa
  namespace: api-gateway-prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-gateway
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300      # 缩容前观察 5 分钟，避免抖动
      policies:
        - type: Percent
          value: 50                        # 每分钟最多缩 50%
          periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 0        # 扩容立即生效
      policies:
        - type: Percent
          value: 100                       # 每分钟最多扩 100%
          periodSeconds: 60
```

> **stabilizationWindowSeconds 为什么重要**：不加这个参数，HPA 会在负载抖动时频繁缩容扩容（"震荡"），导致服务不稳定和资源浪费。

## 7. Ingress 与 TLS

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-gateway
  namespace: api-gateway-prod
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"      # 自动签发 TLS 证书
    nginx.ingress.kubernetes.io/proxy-body-size: "1m"       # 请求体大小限制
    nginx.ingress.kubernetes.io/proxy-read-timeout: "30"
    nginx.ingress.kubernetes.io/limit-connections: "100"    # 单 IP 并发限制
    nginx.ingress.kubernetes.io/limit-rps: "50"             # 单 IP 速率限制
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - api.internal.example.com
      secretName: api-gateway-tls
  rules:
    - host: api.internal.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-gateway
                port:
                  number: 80
```

## 8. 可观测性：Prometheus ServiceMonitor

如果集群装了 Prometheus Operator，用 ServiceMonitor 替代 Pod annotations 更规范：

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: api-gateway
  namespace: api-gateway-prod
spec:
  endpoints:
    - interval: 15s
      path: /metrics
      port: metrics
  selector:
    matchLabels:
      app: api-gateway
```

对应的告警规则（PrometheusRule）：

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: api-gateway-alerts
  namespace: api-gateway-prod
spec:
  groups:
    - name: api-gateway
      rules:
        - alert: HighErrorRate
          expr: rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.05
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "API Gateway 错误率 > 5% 持续 5 分钟"

        - alert: HighLatency
          expr: histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) > 1
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "API Gateway P99 延迟 > 1s"
```

## 9. 一键部署与更新流程

### 首次部署

```bash
# 1. 创建 namespace 和基础资源
kubectl apply -f namespace.yaml
kubectl apply -f rbac.yaml
kubectl apply -f configmap.yaml
kubectl apply -f secret.yaml

# 2. 部署应用
kubectl apply -f deployment.yaml

# 3. 创建服务和入口
kubectl apply -f service.yaml
kubectl apply -f pdb.yaml
kubectl apply -f hpa.yaml
kubectl apply -f ingress.yaml

# 4. 验证
kubectl -n api-gateway-prod get pods -w
kubectl -n api-gateway-prod get hpa
kubectl -n api-gateway-prod describe ingress api-gateway
```

### 滚动更新与回滚

```bash
# 更新镜像
kubectl -n api-gateway-prod set image deployment/api-gateway \
  api-gateway=registry.internal/my-api-gateway:v2.6.0

# 观察滚动更新进度
kubectl -n api-gateway-prod rollout status deployment/api-gateway

# 上线后发现异常——一键回滚
kubectl -n api-gateway-prod rollout undo deployment/api-gateway

# 回滚到指定版本
kubectl -n api-gateway-prod rollout history deployment/api-gateway
kubectl -n api-gateway-prod rollout undo deployment/api-gateway --to-revision=3
```

## 10. 生产验证清单

部署完成后逐项确认：

| 类别 | 检查项 | 命令 |
|---|---|---|
| 基础 | 所有 Pod Running | `kubectl -n api-gateway-prod get pods` |
| 探针 | 无 CrashLoopBackOff | `kubectl -n api-gateway-prod describe pod` 查看 Events |
| 安全 | 用户非 root | `kubectl -n api-gateway-prod exec <pod> -- id` 应输出 uid=1000 |
| 网络 | Service 可达 | `kubectl -n api-gateway-prod run test --rm -it --image=curlimages/curl -- curl -s http://api-gateway/healthz` |
| 弹性 | HPA 正常运行 | `kubectl -n api-gateway-prod get hpa` |
| 可用 | PDB 状态正常 | `kubectl -n api-gateway-prod get pdb` |
| 调度 | Pod 分散在不同节点 | `kubectl -n api-gateway-prod get pods -o wide` 检查 NODE 列 |
| TLS | 证书有效 | `curl -vI https://api.internal.example.com/api/healthz` |

## 常见坑

| 问题 | 现象 | 原因 | 解决 |
|---|---|---|---|
| 滚动更新卡住 | `rollout status` 无限等待 | `maxUnavailable` 和 replicas 冲突；或新 Pod 无法 Ready | `kubectl describe pod` 看探针，调高 `maxUnavailable` 或修复探针 |
| Pod 频繁重启 | `RESTARTS` 列数字持续增长 | `livenessProbe` 配置太严格（如 `initialDelaySeconds` 太短） | 合理使用 `startupProbe`，调低 `livenessProbe.failureThreshold` |
| HPA 震荡 | 副本数上下波动 | 未设置 `stabilizationWindowSeconds` 和 `behavior` | 添加缩放行为策略，缩短指标采集间隔 |
| OOMKilled | Pod 状态 `OOMKilled`，重启次数增加 | `limits.memory` 过低；或应用有内存泄漏 | 调高 limit；如果应用是 Go，加上 `GOMEMLIMIT` 环境变量 |
| PDB 阻塞维护 | `kubectl drain` 超时 | `minAvailable` 设得比正常副本数还大 | PDB 允许中断数 = replicas - minAvailable，至少为 1 |
| Ingress 不通 | 返回 404/503 | Service selector 不匹配；或 Ingress Controller 未安装 | `kubectl describe ingress` 看 Backend；`kubectl get pods -n ingress-nginx` |
| ConfigMap 更新不生效 | 修改 ConfigMap 后 Pod 仍用旧配置 | ConfigMap 挂载为文件不会热更新 | 用 Deployment annotations `checksum/config` 触发滚动；或用 Reloader |

## 小结

- **安全三件套**：`runAsNonRoot` + `readOnlyRootFilesystem` + `drop ALL`，是每个生产 Pod 的底线配置
- **探针三件套**：`startupProbe` 保护慢启动 → `livenessProbe` 自愈卡死 → `readinessProbe` 控制流量接入
- **弹性三件套**：HPA（自动扩缩）+ PDB（自愿中断保护）+ Pod Anti-Affinity（故障域分散）
- 生产部署的本质不是 `kubectl apply` 一下，而是**逐一回答**：安全了吗？监控了吗？能自愈吗？更新会中断吗？出问题了能回滚吗？
