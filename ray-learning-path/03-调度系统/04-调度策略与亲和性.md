# 调度策略与亲和性

## 提出问题

资源够了，节点也有，但 Task A 的结果要给 Task B 用，而 Task B 被调度到了另一个节点——那跨节点搬数据就是浪费。或者反过来，你希望两个 Task 绝对不要跑到同一节点（避免单点故障）。Ray 怎么让你精细控制"谁和谁放在一起/不放在一起"？

## 调度策略总览

```python
from ray.util.scheduling_strategies import (
    PlacementGroupSchedulingStrategy,
    NodeAffinitySchedulingStrategy
)

# 方式 1: 简单策略字符串
@ray.remote(scheduling_strategy="SPREAD")
def spread_task(): ...

# 方式 2: 对象引用（NodeAffinity）
@ray.remote(scheduling_strategy=NodeAffinitySchedulingStrategy(
    node_id="node_abc123",
    soft=False  # 硬亲和：必须在该节点
))
def node_task(): ...

# 方式 3: Placement Group 绑定（上一节已讲）
@ray.remote(scheduling_strategy=PlacementGroupSchedulingStrategy(
    placement_group=pg,
    placement_group_bundle_index=0
))
def pg_task(): ...
```

## DEFAULT 策略深入

默认策略是 Ray 耗时最多优化的调度逻辑，它的决策优先级：

```mermaid
flowchart LR
  n0["数据本地性 (Data Locality)"]
  n1["如果 Task 的参数中有 ObjectRef"]
  n2["→ 优先调度到该 Object 所在的节点"]
  n3["→ 实现零拷贝数据访问"]
  n4["资源可用性 (Resource Availability)"]
  n5["在满足数据本地性的候选节点中"]
  n6["→ 选资源最充足的"]
  n7["负载均衡 (Load Balancing)"]
  n8["在剩余候选节点中"]
  n9["→ 选当前负载最低的"]
  n10["节点亲和 (Node Affinity)"]
  n11["如果设置了软亲和"]
  n12["→ 优先满足亲和性要求"]
  n0 --> n1
  n1 --> n2
  n2 --> n3
  n3 --> n4
  n4 --> n5
  n5 --> n6
  n6 --> n7
  n7 --> n8
  n8 --> n9
  n9 --> n10
  n10 --> n11
  n11 --> n12
```

> **类比**：DEFAULT 是一个"聪明管家"——先去食材在的后厨（数据本地性）→ 再看哪个灶台空着（资源）→ 最后看哪个厨师不忙（负载均衡）。

### 数据本地性的实现

```python
# 实验：观察 Task 被调度到哪个节点
import ray
ray.init()

@ray.remote
def create_data():
    import socket
    print(f"创建数据的节点: {socket.gethostname()}")
    return [1] * 1000000  # 1MB 数据

@ray.remote
def consume(ref):
    import socket
    data = ray.get(ref)
    print(f"消费数据的节点: {socket.gethostname()}")
    return len(data)

ref = create_data.remote()
ray.get(ref)  # 确保创建完成

# 默认策略：consume 会被调度到与 create_data 相同的节点
consume.remote(ref)
# 大概率输出同一个 hostname → 零拷贝访问
```

## SPREAD 策略

SPREAD 强制 Task **均匀分布**到不同节点：

```python
@ray.remote(scheduling_strategy="SPREAD")
def spread_out():
    ...

# 100 个 Task → 尽量分散到所有节点
futures = [spread_out.remote() for _ in range(100)]
```

### SPREAD 的适用场景

1. **水平扩展的 map 操作**：每个 Task 做独立计算，不受数据位置影响
2. **充分利用所有节点**：你有 10 个节点，想全部用上
3. **避免热点**：不希望所有 Task 涌向有大内存的节点

### SPREAD 的决策逻辑

```mermaid
flowchart LR
  n0["SPREAD 算法："]
  n1["计算每个节点的 '负载指数' = 该节点当前 task 数 / 该节点总资源"]
  n2["优先选负载指数最低的节点"]
  n3["如果多个节点相同 → 随机选择"]
  n4["不考虑数据本地性"]
  n0 --> n1
  n1 --> n2
  n2 --> n3
  n3 --> n4
```

## 节点亲和性 (Node Affinity)

### 硬亲和 (Soft=False)

Task **必须**运行在指定节点，否则不执行：

```python
@ray.remote(scheduling_strategy=NodeAffinitySchedulingStrategy(
    node_id="node_abc123",
    soft=False
))
def must_here():
    # 只能在 node_abc123 上跑
    ...

# 如果 node_abc123 不存在或资源不够 → Task 永久等待
```

### 软亲和 (Soft=True)

Task **优先**在指定节点，不行就在其他地方：

```python
@ray.remote(scheduling_strategy=NodeAffinitySchedulingStrategy(
    node_id="node_abc123",
    soft=True
))
def prefer_here():
    ...
```

### 获取节点 ID

```python
# 方法 1: 从 Ray 状态获取
nodes = ray.nodes()
for node in nodes:
    print(f"Node ID: {node['NodeID']}, Alive: {node['Alive']}")

# 方法 2: 在 Task 内获取
@ray.remote
def get_my_node():
    return ray.get_runtime_context().get_node_id()

node_id = ray.get(get_my_node.remote())
```

### 使用场景

1. **GPU 互连优化**：某个模型必须在有 NVLink 的两个 GPU 上跑
2. **数据重力**：一个大数据集存在特定节点的 SSD 上，不想搬数据
3. **许可限制**：只有某台机器有软件许可证

## 环境依赖与 Runtime Env

除了调度位置，有时候还需要特定环境（Python 版本、依赖包）：

```python
# 指定 Task 的运行环境
@ray.remote(runtime_env={
    "pip": ["torch==2.1.0", "transformers"],
    "env_vars": {"MODEL_PATH": "/data/models"},
    "working_dir": "./my_project",        # 上传本地目录
    "py_modules": ["my_module.py"]       # 上传 Python 模块
})
def special_env_task():
    import torch  # 会在指定的 pip 环境中
    ...
```

Runtime Env 与调度策略配合：

```python
# 复杂的配置组合
@ray.remote(
    num_gpus=1,
    scheduling_strategy="DEFAULT",
    runtime_env={
        "pip": ["torch", "transformers"],
        "container": {"image": "my-ray-image:latest"}  # Docker 容器
    }
)
def production_task():
    ...
```

## 反亲和性 (Anti-Affinity)

Ray 没有直接的反亲和 API，但可以通过 Placement Group 的 SPREAD 策略 + 每个节点只放一个 bundle 来实现：

```python
# 需求：4 个 Task 必须分别在 4 个不同节点
from ray.util.placement_group import placement_group

pg = placement_group([
    {"CPU": 1}, {"CPU": 1}, {"CPU": 1}, {"CPU": 1}
], strategy="SPREAD")
ray.get(pg.ready())

# 每个 bundle 绑定到不同节点 → 实现了反亲和
tasks = [
    my_task.options(
        scheduling_strategy=PlacementGroupSchedulingStrategy(
            placement_group=pg, placement_group_bundle_index=i
        )
    ).remote()
    for i in range(4)
]
```

## 调度调试

### 查看 Task 被调度到哪里

```python
@ray.remote
def debug_task():
    ctx = ray.get_runtime_context()
    return {
        "task_id": ctx.get_task_id(),
        "node_id": ctx.get_node_id(),
        "worker_id": ctx.get_worker_id(),
        "assigned_resources": ctx.get_assigned_resources()
    }

info = ray.get(debug_task.remote())
print(info)
# {'task_id': '...', 'node_id': '...', 'assigned_resources': {'CPU': 1.0}}
```

### Dashboard 查看

在 `http://127.0.0.1:8265/#/events` 可以查看每个 Task 的生命周期：
- **WAITING**（等待资源）
- **SCHEDULED**（已调度到节点）
- **RUNNING**（正在执行）
- **FINISHED**（完成）

## 常见陷阱

### 1. 过度使用硬亲和导致资源饥饿

```python
# ❌ 所有 Task 都绑定到特定节点，其他节点空着
for i in range(100):
    task.options(
        scheduling_strategy=NodeAffinitySchedulingStrategy(
            node_id="node_0", soft=False  # 全部去 node_0
        )
    ).remote()

# ✅ 大部分用默认策略，只对必要任务用亲和
```

### 2. 数据本地性 vs 负载均衡的矛盾

有时数据在所有节点上都有副本，但 DEFAULT 策略会固定调度到第一个节点。这时候用 SPREAD 可能更好。

### 3. Runtime Env 太大会降低调度速度

`working_dir` 或 `py_modules` 大的话（几百 MB），每次新节点上第一次使用都需要上传+解压。可以预构建 Docker 镜像解决。

## 小结

- `DEFAULT`：优先数据本地性 → 资源可用 → 负载均衡
- `SPREAD`：强制均匀分布，适合无状态 map
- 节点亲和：硬性（必须在此）或软性（优先在此）
- 反亲和需要 Placement Group 的 SPREAD 实现
- Runtime Env 控制运行环境，配合调度策略使用
- 通过 `ray.get_runtime_context()` 或 Dashboard 调试调度行为
