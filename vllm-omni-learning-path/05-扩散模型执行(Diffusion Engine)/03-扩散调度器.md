## 扩散调度器的两层结构

扩散推理需要**两层调度**：

```mermaid
flowchart TD
  n0["RequestScheduler（请求级）"]
  n1["'现在应该处理哪些用户的请求？'"]
  n2["▼"]
  n3["StepScheduler（步级）"]
  n4["'这个请求当前该执行第几步去噪？'"]
  n5["▼"]
  n6["DiffusionWorker（执行）"]
  n7["'在 GPU 上跑这一步'"]
  n0 --> n1
  n1 --> n2
  n2 --> n3
  n3 --> n4
  n4 --> n5
  n5 --> n6
  n6 --> n7
```

打个比方：RequestScheduler 是餐厅的"排位系统"（决定哪桌客人先上菜），StepScheduler 是"做菜工序"（这道菜该翻面了、该加盐了）。

### 组 Batch 策略

扩散模型对 batch 的要求比 AR 模型严格：

- 同一个 batch 中的所有请求必须有**相同的分辨率**（因为 DiT 的输入形状固定）
- 最好有**相同的步数**（否则步数少的请求完成后要等待步数多的）
- CFG 的"条件+无条件"两个路径需要同时处理

### 请求优先级

调度策略为简单的 FIFO（先来先服务）：
- **FIFO**：waiting 队列按到达顺序调度
- **容量控制**：running 请求数达到上限（`max_num_running_reqs`）后暂停调度新请求

## SchedulerInterface —— 统一接口

[`interface.py`](../../code/vllm-omni/vllm_omni/diffusion/sched/interface.py) 定义了调度器的抽象接口：

```python
class SchedulerInterface(ABC):
    @abstractmethod
    def add_request(self, request): ...

    @abstractmethod
    def schedule(self) -> DiffusionSchedulerOutput: ...

    @abstractmethod
    def update_from_output(self, sched_output, output): ...

    @abstractmethod
    def has_requests(self) -> bool: ...
```

这样 DiffusionEngine 可以切换不同的调度策略而不需要改引擎代码。
