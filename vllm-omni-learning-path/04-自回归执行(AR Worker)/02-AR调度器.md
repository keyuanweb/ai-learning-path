## 调度器的作用

在 vLLM 中，调度器（Scheduler）决定两件事：

1. **哪些请求**在**何时**被处理（请求调度）
2. 每个请求分配多少 **KV Cache 空间**（显存调度）

vLLM-Omni 的 AR Scheduler 在 vLLM 原生 Scheduler 基础上，增加了对**多模态输入**和**多 Stage 协作**的支持。

## 调度器类型

| 调度器 | 适用 Stage | 特点 |
|--------|-----------|------|
| `OmniARScheduler` | thinker（AR Stage） | 支持多模态、KV Cache 跨 Stage 传输 |
| `OmniGenerationScheduler` | talker/code2wav（Gen Stage） | 非自回归，无 KV Cache 累积 |
| `OmniSchedulingCoordinator` | 协调器 | 多 Stage 间的调度协调 |

## OmniARScheduler —— AR 模型的调度器

```python
class OmniARScheduler(Scheduler):
    """
    扩展 vLLM Scheduler：
    - 多模态请求的 prefill：图片/音频 token 的处理
    - KV Cache 传输：标记需要传输给下游的 KV 块
    - 流式输出支持：async_chunk 模式下的调度
    """
```

### 多模态 Prefill 的特殊处理

多模态输入（图片、音频）的处理方式和纯文本不同：

```
纯文本 prefill：
  "你好，请" → [token1, token2, token3, token4] → 一次 prefill

多模态 prefill：
  文本: "描述这张图片："
  图片: [img_tokens...]  ← 图片被编码为一批 token
  → 文本 token + 图片 token 一起 prefill
```

调度器需要确保：
- 图片/音频 token 有足够的 KV Cache 空间
- 多模态 token 的 prefill chunk 大小合理（图片 token 可能很多）
- 多模态 embedding 注入的位置正确

### Chunk Prefill 和多模态

vLLM V1 支持 chunk prefill（长 prompt 分块 prefill），但多模态 token 有特殊要求：
- 同一张图片的所有 token 必须在同一个 chunk 中处理（因为图片特征是整体编码的）
- 调度器通过 `mm_processor_kwargs` 中的信息知道哪些 token 属于同一张图片

## OmniGenerationScheduler —— 非自回归调度器

Generation Worker 使用的调度器比 AR Scheduler 简单很多：

```python
class OmniGenerationScheduler:
    """
    非自回归生成不需要 KV Cache：
    - 每个请求"一次 prefill + 一次 decode"
    - 不需要管理 KV Cache 块
    - 可以同时处理更多并发请求（因为无 KV Cache 累积）
    """
```

## OmniSchedulingCoordinator —— 多 Stage 调度协调

[`omni_scheduling_coordinator.py`](../../code/vllm-omni/vllm_omni/core/sched/omni_scheduling_coordinator.py) 负责多 Stage 间的调度协调：

```
Stage 0 Scheduler ←── 协调器 ──→ Stage 1 Scheduler
       │                              │
  "请求 A 的 KV 准备好了"    "请求 A 可以开始 decode 了"
```

它解决的核心问题：**下游 Stage 何时可以开始处理请求**。这取决于上游 Stage 的 KV Cache 何时就绪。

## 调度输出结构

[`core/sched/output.py`](../../code/vllm-omni/vllm_omni/core/sched/output.py) 定义了调度器的输出结构（`SchedulerOutput`），它告诉 Worker：

- 这次 step 应该计算哪些 token
- 哪些请求是 prefill（需要预填充 KV Cache）
- 哪些请求是 decode（只需算一个新 token）
- 哪些 KV 块需要传输给下游 Stage
