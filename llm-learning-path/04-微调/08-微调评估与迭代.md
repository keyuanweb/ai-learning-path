# 微调评估与迭代

"模型变好了吗？" 这个问题并不简单。微调后的评估需要多维度、多层次的判断。

---

## 1. 自动评估 vs 人工评估

### 自动评估的悖论

用 GPT-4 评判微调后的模型，但 GPT-4 本身就是"好"的标准之一。这类似于用尺子量另一把尺子——两者都有误差，但相对比较仍然有效。

### 评估金字塔

```
        人工深度评估 (最准但最贵)
       /
    LLM-as-Judge (高性价比)
     /
  标准化 Benchmark (快速但片面)
```

---

## 2. LLM-as-a-Judge

### 怎么做

用最强模型（如 GPT-4 或 Claude 3.5）作为裁判，比较微调前后的回答质量。

```python
eval_prompt = f"""请评判以下两个回答的质量。只输出 "A更好"、"B更好" 或 "差不多"。

[问题]: {question}

[回答A]: {response_before_finetune}
[回答B]: {response_after_finetune}

评判标准:
1. 是否准确回答了问题
2. 是否清晰易懂
3. 是否提供了足够的细节
4. 是否有事实错误
"""
```

### 评估维度

| 维度 | 描述 |
|------|------|
| **有用性 (Helpfulness)** | 是否真正解决了用户的问题 |
| **真实性 (Truthfulness)** | 是否有编造的事实 |
| **安全性 (Safety)** | 对有害请求是否正确拒绝 |
| **完整性 (Completeness)** | 是否回答了问题的所有方面 |
| **格式 (Format)** | 是否遵循了要求的输出格式 |

### LLM-as-Judge 的局限

- **位置偏差**：GPT 倾向于说"B 更好"（位置偏见）
- **长度偏见**：倾向于认为更长的回答更好
- **自我偏好**：GPT-4 可能偏好 GPT-4 风格的输出
- **缓解**：随机交换 A/B 位置、设置长度惩罚、使用交叉验证

---

## 3. 标准化 Benchmark

### 微调后必测的 Benchmark

| Benchmark | 测试内容 | 最小提升预期 |
|-----------|----------|------------|
| **AlpacaEval** | 指令跟随通用能力 vs GPT-4 | win rate > 50% |
| **MT-Bench** | 多轮对话能力 (GPT-4 打分) | 提升 1-2 分 |
| **MMLU** | 多领域知识 | 不退化（微调应保持预训练知识） |
| **HumanEval** (如果微调代码) | 代码生成 | Pass@1 提升 |

---

## 4. 微调迭代循环

```
1. 建立基线: 用当前模型回答 100 个代表性 prompt
2. 找出失败模式:
   - 哪些类型的 prompt 失败率高？
   - 错误是"不知道"还是"编造"？
   - 格式错误 vs 内容错误？
3. 针对性补充训练数据:
   - 为失败模式生成更多 SFT 数据
   - 为偏好错误生成更多 DPO 数据
4. 重新微调 + 评估
5. 对比: 失败模式是否改善？其他维度是否退化？
```

### 灾难性遗忘检测

微调后模型可能在目标任务上变好，但在通用能力上下降。检测方法：
- 微调前后各跑一遍 MMLU，确认无显著下降
- 保留一批"不相关"的测试 prompt，确认微调没有破坏它们

---

## 5. 评估清单

```
□ AlpacaEval: win rate vs GPT-4 或 baseline
□ MT-Bench: 多轮对话评分
□ Domain-specific: 你自己的测试集
□ Safety: 确认模型正确拒绝有害请求
□ Factuality: SimpleQA 或类似数据集
□ Regression: MMLU 确保没有遗忘
□ Human Eval: 抽查 100 条 (最重要的环节)
□ A/B Test: 如果上线，10% 流量做 A/B
```
