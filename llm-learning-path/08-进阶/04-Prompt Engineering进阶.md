# Prompt Engineering 进阶

Prompt Engineering 不是"写提示词的小技巧"，而是系统化地设计 LLM 的输入上下文，让它准确理解意图并输出期望结果。

---

## 1. 从 Prompt 到 Context Engineering

### 思维转变

```
低阶认知: Prompt = 一句提问
进阶认知: Prompt = 构建给 LLM 的完整工作环境（指令 + 示例 + 数据 + 约束）
```

**Context Engineering = 把正确的信息、用正确的格式、在正确的时间放入 LLM 的上下文窗口。**

---

## 2. Few-shot：用例子教会 LLM

### 解决的问题

LLM 知道"要做什么"但不确定"怎么做"——格式、风格、输出结构。

### 做法

在 prompt 中给 2-5 个完整的输入→输出示例：

```text
将以下评论分类为：正面/负面/中性

评论：等了两个小时，菜还是冷的。
分类：负面

评论：性价比挺高，味道还行，就是位置偏了点。
分类：中性

评论：服务员态度特别好，孩子打翻了汤立刻帮忙处理，感动。
分类：正面

评论：{新评论}
分类：
```

### 为什么有效

LLM 的 Attention 机制在读取 prompt 时会"看到"示例中的模式，然后应用到新输入。这不是微调，但效果在很多场景接近微调。

### 关键技巧

- **示例与真实输入尽量相似**——类别标签、输入格式要一致
- **示例标注要绝对正确**——一个错的示例比没有示例更糟
- **输入最后放待分类的数据**——让模型从模式自然过渡到任务

## 3. Chain-of-Thought：让 LLM 写草稿

### 解决的问题

直接要答案 → LLM 跳步 → 推理错误。就像心算 23×17 不打草稿容易错。

### 做法

告诉 LLM"一步步思考"或在示例中展示推理步骤：

```text
问：一个苹果 3 元，小明买了 4 个，付了 20 元，找回多少？

一步步想：
1. 4 个苹果共 4×3 = 12 元
2. 付了 20，找回 20-12 = 8 元
3. 答案：8 元

---
问：{新问题}
一步步想：
```

### 为什么有效

Auto-Regressive Generation——每个生成的 token 成为后续 token 的条件。让模型先"说出"推理中间步骤等价于给后续推理提供了中间结果。

### CoT 的变体

| 变体 | 做法 | 场景 |
|------|------|------|
| **Zero-shot CoT** | 加一句 "Let's think step by step" | 通用推理 |
| **Few-shot CoT** | 示例中展示推理步骤 | 复杂推理 |
| **Self-Consistency** | 运行 CoT 多次，取多数答案 | 提升准确性 |
| **Tree-of-Thought** | 探索多条推理路径，回溯选择 | 规划和搜索问题 |
| **ReAct** | CoT + 工具调用交替 | Agent 场景 |

## 4. 提示词设计的结构化方法

### CO-STAR 框架

| 要素 | 英文 | 含义 | 示例 |
|------|------|------|------|
| **C** | Context | 背景信息 | "你是一个资深 Python 开发者" |
| **O** | Objective | 具体目标 | "请 review 以下代码" |
| **S** | Style | 输出风格 | "使用专业但友好的语气" |
| **T** | Tone | 情感基调 | "保持建设性，不要指责" |
| **A** | Audience | 目标读者 | "面向初级开发者" |
| **R** | Response | 输出格式 | "用清单列出问题和建议" |

### 完整示例

```text
# Context
你是某大厂技术委员会成员，正在审查一个核心模块的 PR。

# Objective
对以下代码做 code review，识别潜在的性能问题和安全隐患。

# Style & Tone
专业、建设性。指出问题时简要说明原因，高危问题需要建议修改方案。

# Audience
代码作者是有 2 年经验的 Python 开发者，但对异步编程不太熟悉。

# Response Format
1. 高危问题（必须修改）：[问题] → [原因] → [建议]
2. 改进建议：[问题] → [原因] → [建议]
3. 优秀之处：[点出做得好的地方]

# Code
{paste_code_here}
```

## 5. 常见陷阱

### 提示词太长

模型有上下文窗口限制。当 prompt 太长 → 模型可能"遗忘"中间的信息（Lost in the Middle 效应）。

**对策**：关键指令放在 prompt 开头和结尾（人类阅读也一样，首尾最重要）。

### 要求太多

"请写一篇关于 AI 的文章，要幽默、有数据支撑、引用最近论文、配上代码示例、分 5 个章节、每章 200 字..." → LLM 可能只完成部分要求。

**对策**：分步骤——先用一个 prompt 规划大纲，再用后续 prompt 逐个章节生成。

### 负面指令

"不要使用 ChatGPT 这种语气"、"不要提到 OpenAI"——LLM 对否定指令的处理不如正面指令。

**对策**：用正面表述代替。"以学术论文的语气"代替"不要用聊天语气"。

## 6. System Prompt 的设计

System Prompt 是整个对话的"约束层"，优先级最高。

```text
你是一个技术文档写作助手，请遵守以下规则：

1. 回答前如果信息不够，先说明你"不确定"的部分，不要猜测
2. 回答包含代码时，默认使用 Python，标注必要依赖
3. 每次回答简洁但完整——先给直接答案，再给解释
4. 涉及版本号时，默认指 2025 年 5 月的最新稳定版本
```

**关键原则**：System Prompt 设约束，User Prompt 描述任务。不要让 User Prompt 重复 System Prompt 的内容。

## 本章速查

| 技巧 | 一句话 | 何时用 |
|------|--------|--------|
| **Few-shot** | 给 2-5 个示例 | 格式或风格有特殊要求 |
| **CoT** | 让 LLM 写推理过程 | 数学/逻辑/代码推理 |
| **CO-STAR** | 结构化 prompt 框架 | 所有正式场景 |
| **Self-Consistency** | CoT 跑多次取多数 | 需要高准确率 |
| **首尾效应** | 关键信息放开头和结尾 | 长 prompt |

**记住这个就够了**：Prompt Engineering 的核心不是"写得好"，而是"给模型提供正确的工作环境"——把指令、示例、数据和约束以正确的顺序放入上下文。
