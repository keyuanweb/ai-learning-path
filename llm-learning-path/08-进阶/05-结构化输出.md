# 结构化输出

LLM 的输出是自由文本，但生产系统需要确定的、可解析的格式。结构化输出让 LLM 在"创意"和"确定性"之间找到平衡点。

---

## 1. 解决的问题

### 为什么自由文本不够

```python
# LLM 返回的自由文本
"我觉得这个人的名字是张三，年龄大概 28 岁，地址在北京朝阳区"

# 你想从这段话中提取结构化数据 → 正则？字符串分割？
# 每种写法都很脆弱，LLM 换个说法你的解析就崩了
```

### 解决方案

让 LLM 直接输出 JSON/Markdown 表格/特定格式，而不是自然语言。

```
输入: "张三，28岁，住在北京朝阳区"
输出: {"name": "张三", "age": 28, "city": "北京", "district": "朝阳区"}
```

---

## 2. JSON Mode：强制 JSON 输出

### 基本用法

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "提取实体信息..."}],
    response_format={"type": "json_object"}  # 强制返回 JSON
)

result = json.loads(response.choices[0].message.content)
```

### JSON Mode 的问题

- **格式随机**：同一个人名，有时返回 `"name": "张三"`，有时 `"person_name": "张三"`
- **类型不稳定**：数字有时是 `"number"` 有时是 `"数字"`
- **缺失字段**：找不到的就省略，不保证 Schema 完整

## 3. Structured Output / JSON Schema

### 解决方案演进

2024-2025 年主流 API 开始支持 **Structured Output**：你必须先定义 JSON Schema，模型必须严格遵循。

```python
from pydantic import BaseModel, Field
from typing import Optional

# 定义输出结构
class PersonExtraction(BaseModel):
    name: str = Field(description="人名")
    age: Optional[int] = Field(description="年龄，如果没提到就填 null")
    city: str = Field(description="城市")
    district: Optional[str] = Field(description="区县")

# OpenAI / 部分兼容 API
response = client.beta.chat.completions.parse(
    model="gpt-4o",
    messages=[...],
    response_format=PersonExtraction  # 直接传入 Pydantic model
)

# 自动解析好的对象
person = response.choices[0].message.parsed
print(person.name)  # "张三"
```

### 为什么用 Pydantic

- 类型安全（`age` 一定是 int 或 null，不会是 string）
- 自动生成 JSON Schema（你写 Python，Pydantic 转成 JSON Schema 发给 API）
- 自动解析（API 返回的 JSON 自动转回 Python 对象）

## 4. Grammar 约束 (llama.cpp / vLLM)

### 开源模型的方案

闭源 API 内置了 Structured Output。开源部署（llama.cpp、vLLM、SGLang）使用 **Grammar 约束**：在解码时限制每一步只能生成符合语法规则的 token。

```python
# llama.cpp 的 Grammar 约束
grammar = """
root ::= person
person ::= "{" ws "\"name\":" ws string "," ws "\"age\":" ws number "}"
string ::= "\"" [a-zA-Z\s]* "\""
number ::= [0-9]+
ws ::= [ \t\n]*
"""

output = llama.generate(
    prompt,
    grammar=grammar  # 强制输出符合此语法
)
```

### 工作原理

在每一步选择下一个 token 时，过滤掉那些不符合语法规则的 token。只有"合法"的 token 能留在候选列表中。

### 几大框架的 Grammar 支持

| 框架 | 方案 | 易用性 |
|------|------|--------|
| **llama.cpp** | GBNF Grammar | 需要手写语法规则 |
| **vLLM** | Guided Decoding (via outlines/lm-format-enforcer) | 支持 JSON Schema 自动转 Grammar |
| **SGLang** | `regex` 参数 | 直接写正则表达式 |
| **Guidance** | 模板内嵌约束 | 最易用 |
| **Outlines** | Pydantic → Grammar | 自动转换 |

## 5. 错误恢复策略

即使有 Schema 约束，LLM 仍可能输出有问题的 JSON（截断、幻觉字段、格式略微偏差）。

```python
import json

def robust_parse(llm_output: str, schema_model):
    """多层防御的 JSON 解析"""
    # 层 1：直接 parse
    try:
        return schema_model(**json.loads(llm_output))
    except:
        pass

    # 层 2：从 markdown 代码块中提取 JSON
    import re
    match = re.search(r'```json\s*(.*?)\s*```', llm_output, re.DOTALL)
    if match:
        try:
            return schema_model(**json.loads(match.group(1)))
        except:
            pass

    # 层 3：用 LLM 修正
    corrected = llm.generate(
        f"以下 JSON 格式有问题: {llm_output[:500]}\n"
        f"请返回符合此 Schema 的正确 JSON: {schema_model.model_json_schema()}"
    )
    return schema_model(**json.loads(corrected))

    # 层 4（最后手段）：部分字段恢复
    # 尝试逐个字段从原始文本中正则提取
```

## 6. 实战建议

| 建议 | 原因 |
|------|------|
| **Field description 决定质量** | LLM 根据 description 判断该填什么，不是根据 field name |
| **Optional 字段大胆用** | 不是所有信息都在输入中存在 |
| **枚举约束优先** | `Literal["正面", "负面", "中性"]` 比自由 string 可靠 100 倍 |
| **数字字段给范围** | `ge=0, le=150` 约束年龄范围，防止 LLM 生成 328 岁 |
| **复杂拆成多步** | 一个 Schema 50 个字段 → 拆成 5 次提取，每次 10 个字段 |

| 方案 | 适用场景 |
|------|---------|
| **JSON Mode** | 简单场景，对 Schema 一致性要求不高 |
| **Structured Output (API)** | 闭源 API，要强类型保证 |
| **Grammar (开源)** | 本地部署，需要强制格式 |
| **Pydantic** | Schema 定义的事实标准 |
| **多层解析** | 任何生产环境都需要的容错措施 |

**记住这个就够了**：结构化输出 = Pydantic 定义 Schema + API/Grammar 强制执行 + 多层解析兜底。
