# 多轮对话系统设计

单轮问答 = 一问一答，无记忆。多轮对话 = 每一轮都建立在对上一轮的理解之上。这是客服、教育、销售等场景的基础设施。

---

## 1. 核心挑战

### 三个关键问题

| 问题 | 示例 |
|------|------|
| **指代消解** | 用户："上次说的那个方案呢？" →"那个"指什么？ |
| **话题流转** | 从产品咨询突然转到售后投诉 → 系统需要感知 |
| **记忆长度** | 100 轮对话后，第 3 轮的承诺还在上下文中吗？ |

---

## 2. 上下文管理

### 策略 1：全量保留（最简单）

把所有对话历史都塞进 prompt。适用于短对话（<10 轮）。

```python
messages = [
    {"role": "system", "content": "你是客服助手"},
    {"role": "user", "content": "我想退货"},
    {"role": "assistant", "content": "请提供订单号"},
    {"role": "user", "content": "ORD-12345"},
    # ... 无限追加
]
response = llm.chat(messages)
```

**问题**：对话超过 10 轮后 prompt 太长，Token 成本急剧上升，模型还可能出现 Lost in the Middle 效应。

### 策略 2：滑动窗口

只保留最近 N 轮对话。

```python
MAX_ROUNDS = 10
messages = full_history[-MAX_ROUNDS * 2:]  # 每轮 2 条消息（用户+助手）
```

**问题**：超出窗口的信息完全丢失。"我开头问的那个问题你还没回答呢"→ 模型已经忘了。

### 策略 3：摘要压缩

用 LLM 定期把历史对话压缩成摘要。

```python
def compress_history(messages):
    old_messages = messages[:-10]  # 除了最近 5 轮
    recent_messages = messages[-10:]

    summary = llm.generate(
        f"用一段话总结以下对话的关键信息（用户需求、已解决问题的简要列表、待解决问题）：\n{old_messages}"
    )
    return [
        {"role": "system", "content": f"之前的对话摘要: {summary}"}
    ] + recent_messages
```

**本质**：用 LLM 自身的理解能力来管理 LLM 的上下文限制。

## 3. 记忆系统

### 三级记忆架构

```
工作记忆 (Working Memory)   = 最近 N 轮对话（全量保留）
短期记忆 (Short-term)        = 本次会话的历史摘要（定期压缩）
长期记忆 (Long-term)         = 跨会话的用户画像/偏好（数据库持久化）
```

### 长期记忆实现

```python
# 会话结束时，提取关键信息存入用户画像
def update_user_profile(session_history, user_id):
    profile = llm.generate(
        f"从这段对话中提取用户的偏好、需求和关键信息，"
        f"用 JSON 格式：\n{session_history}"
    )
    db.update(f"user:{user_id}", profile)

# 下次用户进入时，注入画像
def get_personalized_prompt(user_id):
    profile = db.get(f"user:{user_id}")
    return f"用户画像: {profile}\n\n请个性化地回应用户。"
```

### 记忆系统的关键设计

- **提取精度**：提取用户信息时可能出错 → 让用户可查看和修正自己的画像
- **遗忘曲线**：时间久远的信息应该被主动精简（不活跃的信息降权重）
- **隐私**：用户画像存储需要脱敏，且提供删除选项

## 4. 对话状态追踪

### 为什么需要

客服 AI 需要知道"当前在哪个流程中"——收集信息？等待确认？处理退款？

### 状态机设计

```
[初始] → 收集订单号 → 核验订单 → 确认问题 → [分支]
                                    ├→ 退款流程 → 确认退款 → 结束
                                    └→ 换货流程 → 确认地址 → 结束
```

```python
class DialogueStateMachine:
    def __init__(self):
        self.state = "initial"
        self.slots = {}  # 收集到的信息槽位
        self.transitions = {
            "initial":       {"next": "collect_order_id"},
            "collect_order_id": {"next": "verify_order", "slot": "order_id"},
            "verify_order":  {"branches": {"valid": "collect_issue", "invalid": "collect_order_id"}},
            "collect_issue": {"next": "confirm_action"},
            "confirm_action":{"branches": {"refund": "process_refund", "exchange": "process_exchange"}},
        }
    
    def progress(self, current_state, extracted_info):
        """基于 LLM 提取的信息推进状态"""
        # LLM 从用户输入中提取结构化信息
        # "我的订单号是 ORD-123" → {"order_id": "ORD-123"}
        self.slots.update(extracted_info)
        # 检查槽位是否填满 → 推进到下一状态
        ...
```

**实践中**：状态机 + LLM 信息提取 = 确定性流程 + 灵活性。

## 5. 多轮对话中的上下文学习

### 挑战

用户的负反馈出现在对话中间："不对，不是这个意思。" 传统方案中这条信息可能被淹没在后续的对话中。

### 解决方案：分层 Prompt

```text
[System] 你是客服助手...

[Context] 用户当前处于退款流程，已收集信息：订单号 ORD-123

[Recent Dialogue]
用户: 不对，我不是要退款，我要换货！  ← 重要反馈
助手: 好的，为您转为换货流程...

[Older Summary] 
用户昨天咨询过物流问题，已解决。

[Current Query]
用户: 换成 M 号吧
```

结构化的 prompt 让信息分层组织，关键上下文（纠错、意图切换）始终在最近消息中。

## 6. 对话评估

| 指标 | 怎么算 |
|------|--------|
| **任务完成率** | 预定目标（退款/咨询/注册）是否达成 |
| **平均轮次** | 完成一个任务需要几轮对话（越少越好） |
| **用户重复意图次数** | 用户说"我不是这个意思"的次数（越少越好） |
| **信息收集效率** | 一轮中收集到几个槽位信息 |
| **用户满意度** | 对话结束后的反馈 |
