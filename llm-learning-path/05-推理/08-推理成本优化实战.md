# 推理成本优化实战

大模型推理的成本管理是决定项目盈亏的关键。本章提供量化决策的工具。

---

## 1. 成本从哪来

### 推理成本的组成

| 成本项 | 占比 | 影响因素 |
|--------|------|---------|
| GPU 租用 | 60-80% | 模型大小、并发量、GPU 型号 |
| 网络带宽 | 5-10% | 输入/输出 token 量 |
| 存储 | 5-10% | 模型权重存储、KV Cache |
| 运维 | 5-10% | 监控、日志、自动扩缩 |

### Token 经济学

```
输入 token:  $0.01 / 1K tokens (嵌入 + 计算 KV Cache prefill)
输出 token:  $0.03 / 1K tokens (自回归生成, 每步读 KV Cache)
```

输出 token 比输入 token 贵 2-3×，因为生成阶段的 GPU 利用率低（计算量少但显存带宽吃满）。

## 2. GPU 选型

### 性价比对比（以 7B 模型推理为例）

| GPU | 显存 | 估量吞吐 (7B BF16) | 云成本/hr | 成本/1M tokens |
|-----|------|-------------------|-----------|---------------|
| RTX 4090 | 24 GB | ~2000 tokens/s | ~$0.5 | ~$0.07 |
| A100 80G | 80 GB | ~4000 tokens/s | ~$2.5 | ~$0.17 |
| H100 80G | 80 GB | ~8000 tokens/s | ~$5.0 | ~$0.17 |
| A10 | 24 GB | ~1500 tokens/s | ~$1.0 | ~$0.19 |
| L4 | 24 GB | ~1200 tokens/s | ~$0.7 | ~$0.16 |
| T4 | 16 GB | ~800 tokens/s | ~$0.4 | ~$0.14 |

RTX 4090 性价比最高（消费卡），但对并发支持有限（24GB 显存 vs 80GB A100 可以处理更大的 batch）。

## 3. 量化：成本优化的最直接手段

### 量化 vs 精度 vs 成本的权衡

| 精度 | 显存 (7B) | 吞吐 | 质量损失 | 适用 |
|------|----------|------|---------|------|
| BF16 | 14 GB | 1× | 0% | 不差钱 |
| INT8 | 7 GB | 1.5-2× | <0.5% | 标准部署 |
| INT4 (AWQ) | 4 GB | 2-3× | ~1-2% | 高性价比 |
| INT4 (GPTQ) | 4 GB | 2-3× | ~1-2% | GPU 推理 |
| Q4_K_M (GGUF) | 4 GB | CPU: 慢 | ~2-3% | 边缘设备 |

### 推荐的量化部署方案

```python
# 方案1: AWQ 量化 + vLLM (GPU)
from vllm import LLM
llm = LLM(model="TheBloke/Llama-3-8B-AWQ", quantization="awq")

# 方案2: GGUF + llama.cpp (CPU/边缘)
llm = Llama(model_path="llama-3-8b.Q4_K_M.gguf", n_ctx=4096)
```

## 4. 批处理策略的经济学

### Batch Size 的权衡

```
小 batch (1-4):
  + 低延迟 (每个请求不需要等待)
  - 低吞吐 (GPU 利用率 <30%)
  - 高成本/请求

大 batch (16-32):
  + 高吞吐 (GPU 利用率 >80%)
  + 低成本/请求
  - 高延迟 (请求需要排队)
```

### 延迟 vs 成本不是线性的

高负载下，自然形成大 batch → 吞吐最高 → 单位 token 成本最低。低负载时考虑"延迟优先"策略（请求一到立即处理，不等攒 batch）。

## 5. 缓存策略：减少重复计算

### Prompt Caching

相同的 system prompt 或 RAG context，只计算一次 KV Cache：

```
system prompt: 3K tokens → KV Cache 计算 50ms
如果 100 个请求使用相同的 system prompt → 省 99 × 50ms = ~5 秒
```

vLLM 和 SGLang 内置 prefix caching，自动处理。

### Response Caching

对高频相同问题（如 FAQ）直接缓存回答，不需要模型推理：

```python
cache = {}
def cached_generate(prompt):
    key = hash(prompt)
    if key in cache:
        return cache[key]  # 直接返回，零 GPU 消耗
    response = llm.generate(prompt)
    cache[key] = response
    return response
```

对于客服、教育等场景，10-30% 的请求可能命中缓存。

## 6. 成本优化检查清单

```
□ 使用量化模型 (AWQ/INT4) — 省 60-70% 显存
□ 选择性价比 GPU (RTX 4090/A100 而非 H100) — 省 50-80% 租金
□ 开启 prefix caching — 省 20-30% prefill 计算
□ 热点问题 response caching — 省 10-30% 请求
□ 设置合理的 max_seq_len (不要设为最大值) — 省显存
□ 高峰期弹性扩容 + 低峰期缩容 — 省 20-40% 闲置成本
□ 使用 GQA 模型 (LLaMA 3, Qwen 2.5+) — 省 50% KV Cache
□ 评估自建 vs API (OpenAI/groq) — API 对小流量更便宜
```
