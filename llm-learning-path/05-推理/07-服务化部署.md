# 服务化部署

从"模型能推理"到"用户能调用"之间有大量工程工作。本章覆盖将大模型部署为生产级 API 服务的关键环节。

---

## 1. FastAPI + vLLM：最小可行的推理服务

```python
from fastapi import FastAPI
from pydantic import BaseModel
from vllm import LLM, SamplingParams
import asyncio

app = FastAPI()
llm = LLM(model="meta-llama/Llama-3-8B", dtype="bfloat16")

class ChatRequest(BaseModel):
    messages: list[dict]
    max_tokens: int = 256
    temperature: float = 0.7

class ChatResponse(BaseModel):
    content: str
    usage: dict

@app.post("/v1/chat/completions", response_model=ChatResponse)
async def chat(request: ChatRequest):
    # 用 asyncio 防止阻塞事件循环
    result = await asyncio.to_thread(llm.generate, request.messages, ...)
    return ChatResponse(content=..., usage=...)
```

### 生产化需要考虑

| 环节 | 问题 | 方案 |
|------|------|------|
| **并发** | 多个请求同时到达 | vLLM continuous batching 自动处理 |
| **超时** | 某些请求生成过长 | 设置 max_tokens + 总超时 |
| **限流** | 防止单个用户滥用 | Rate limiter（按 IP/API Key） |
| **鉴权** | 防止未授权访问 | API Key 认证 |
| **健康检查** | 服务挂了自动重启 | /health endpoint + k8s liveness probe |

## 2. 多模型部署

### 问题

你可能需要同时部署多个模型：主对话模型（70B）、代码补全模型（7B）、embedding 模型（部署 API）、奖励模型。每张 GPU 怎么分配？

### GPU 分片策略

| 策略 | 做法 | 适用 |
|------|------|------|
| **模型多副本** | 每张 GPU 独立运行完整的模型推理 | 轻量模型 (≤7B) |
| **张量并行** | 大模型跨多 GPU 切分 | 70B+ 模型 |
| **混合部署** | GPU 0-3: 70B 模型 (TP=4)，GPU 4: Embedding 模型 | 多模型共存 |

### NVIDIA Triton Inference Server

专业的模型服务编排平台，支持多模型、多框架、动态批处理：

```yaml
# model_repository/llm_model/config.pbtxt
name: "llama_3_8b"
backend: "vllm"
max_batch_size: 32
instance_group [{ count: 1, kind: KIND_GPU }]
```

### GPU 级别的动态调度

更精细的做法：维护一个请求队列，根据当前 KV Cache 使用情况动态分配：

```python
# 选择 KV Cache 利用率最低的 GPU
def select_gpu(request):
    utilizations = [gpu.kv_cache_used / gpu.kv_cache_total for gpu in gpus]
    selected = argmin(utilizations)
    return selected
```

## 4. 弹性伸缩

### 基于队列长度的自动扩缩

```yaml
# Kubernetes HPA 配置
metrics:
  - type: External
    external:
      metric:
        name: inference_queue_length
      target:
        type: AverageValue
        averageValue: 10   # 每个 GPU 平均超过 10 个请求就扩容
```

### 冷启动的代价

模型加载（读权重 → GPU 显存）可能需要 1-10 分钟。这对"无服务器"（serverless）架构是致命的。

**缓解方案**：
- 保持至少 1 个 warm pod（即使无流量）
- 使用模型预热（pre-load 到共享存储）
- 考虑"请求排队等待"而非"立即扩容"（如果队列很短）

## 5. 监控与告警

```python
# 关键指标
metrics = {
    "tokens_per_second": ...,      # 吞吐量
    "time_to_first_token": ...,    # 首 token 延迟 (TTFT)
    "time_per_output_token": ...,  # 每 token 延迟 (TPOT)
    "queue_length": ...,           # 排队请求数
    "kv_cache_utilization": ...,   # KV Cache 使用率
    "gpu_utilization": ...,        # GPU SM 利用率
    "error_rate": ...,             # 错误率
    "p50/p95/p99_latency": ...,   # 延迟分位数
}
```

| 告警 | 条件 | 处理 |
|------|------|------|
| 高延迟 | P95 > 2× 基线 | 检查是否过载/内存压力 |
| 低吞吐 | tokens/s 骤降 50% | 检查是否为坏节点 |
| OOM | GPU 显存接近 100% | 减短 max_seq_len，或加 GPU |
| 高错误率 | error rate > 1% | 检查模型是否损坏 |
