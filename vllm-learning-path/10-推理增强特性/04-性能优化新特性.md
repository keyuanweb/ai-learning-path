# 04 · 性能优化新特性：DBO + MRV2

> ⚠️ 本文涵盖的功能均为开发中或实验性特性，API 和架构尚未稳定。

## Dual Batch Overlap (DBO)

**设计文档**：[`code/vllm/docs/design/dbo.md`](../../code/vllm/docs/design/dbo.md)
**源码**：[`code/vllm/vllm/v1/worker/gpu_ubatch_wrapper.py`](../../code/vllm/vllm/v1/worker/gpu_ubatch_wrapper.py)

### 动机

MoE 模型的推理包含 all-to-all 通信（dispatch + combine）。在传统执行流程中，通信和计算是**串行**的：

```
[Compute A] → [Dispatch (阻塞)] → [Compute Expert] → [Combine (阻塞)] → [Compute B]
```

GPU 在等待通信时处于空闲状态。DBO 通过**双 micro-batch 乒乓调度**重叠通信与计算。

### 核心思想

将 batch 拆分为两个 micro-batch（μ-batch₀ 和 μ-batch₁），用两个 CPU 线程交替执行：

```python
# 重叠调度示意
# Comp: |-A0₀-A1₀-||-MLP₁-||-S₁-MLP₀-||-S₀-A0₁-A1₁-|
# Comm: |----D₁---||--D₀--||----C₁---||-----C₀-----|
# 
# 其中: A0 = MLA qkv proj, A1 = Core attn + out proj + MoE gate
#       D = Dispatch, C = Combine, S = Shared expert
```

关键：当 thread₀ 在执行 Compute 时，thread₁ 正在等待 Dispatch/Combine。两者交替，GPU 不再空等通信。

### 组件

| 组件 | 文件 | 职责 |
|------|------|------|
| **UBatchWrapper** | `gpu_ubatch_wrapper.py` | 管理线程生命周期、CUDA Graph 执行 |
| **UBatchContext** | `ubatch_utils.py` | 协调两个 UBatch 线程的同步 |
| **GPUModelRunner (修改)** | `gpu_model_runner.py` | Batch 拆分 + AttentionMetadata 切片 |

### 要求与限制

- 部署模式：**DP + EP**（Data Parallel + Expert Parallel）
- 通信后端：**DeepEP**（`--all2all-backend deepep_low_latency`）
- 至少 2 GPU（`CUDA_VISIBLE_DEVICES`）
- 需 DP 全 rank 一致决定是否启用 micro-batching（若任一个 rank 不满足条件则全体禁用）

### 启用

```bash
vllm serve deepseek-ai/DeepSeek-V2-Lite \
  --trust-remote-code \
  --data-parallel-size 2 \
  --enable-expert-parallel \
  --enable-dbo \
  --all2all-backend deepep_low_latency
```

可选参数：
- `--dbo-decode-token-threshold`：decode batch 的最小 token 数才会触发 DBO
- `--dbo-prefill-token-threshold`：prefill batch 的最小 token 数才会触发 DBO

## Model Runner V2 (MRV2)

**设计文档**：[`code/vllm/docs/design/model_runner_v2.md`](../../code/vllm/docs/design/model_runner_v2.md)

### 为什么重写

V1 的 GPUModelRunner 在几年迭代中积累了显著的技术债务：

1. **Persistent Batch 过度耦合**：持久化状态张量直接用作模型输入，导致插入/删除请求时需要复杂重排
2. **异步支持不充分**：V1 最初未设计异步调度，后续的 async 支持是"打补丁"式的
3. **CPU 同步点过多**：多次 `torch.accelerator.synchronize` 和隐式 `.to("cuda")` 阻碍 GPU/CPU 重叠
4. **Modularity 不够**：~7800 行单文件，功能耦合严重

### MRV2 五大改进

#### 1. Persistent Batch（解耦版）

V1 问题：持久化状态张量直接用作模型输入。

MRV2 方案：
- 预分配固定大小张量（`max_num_reqs` 行，默认 1024）
- 每个请求分配一个**永久行**，从创建到完成/抢占
- **GPU Gather**：从持久状态张量中按索引搜集输入，而非 CPU 重建
- 无需 `CachedRequestState` 备份

#### 2. Async-First

MRV2 从第一性原理设计就假定异步调度：
- 核心执行循环是纯 CUDA stream，无 CPU 同步点
- CPU 将工作排队到 stream 上，不做阻塞等待
- Scheduler/Worker 为 step N+1 做 CPU 准备工作时，GPU 正在执行 step N

#### 3. Removing Async Barrier

消除异步数据竞争的新方法：
- `StagedWriteTensor`：分阶段的 GPU 写入，用 packed diffs 增量更新大张量
- pinned memory 技巧：数据先写到 pinned memory，再批量 GPU 拷贝
- 零 `torch.cuda.synchronize()` 调用

#### 4. GPU-Native Input Metadata

用 Triton kernel 在 GPU 侧构建输入元数据：
- 利用 **UVA（Universal Virtual Addressing）** 实现 CPU/GPU 统一寻址
- Block tables、positions 等大张量直接在 GPU 上构建
- 避免 CPU → GPU 的大规模数据传输

#### 5. Triton-Native Sampler

采样在 Triton kernel 中执行：
- **Gumbel-max 采样**：在单 kernel 中完成（vs. PyTorch eager 的多步操作）
- 高效的 top-k logprobs 提取
- 内存高效的 prompt logprobs 计算

### 状态

MRV2 仍在**开发中**：
- ✅ 核心架构（Persistent Batch、Async-First、StagedWriteTensor）
- ⚠️ 功能完整性（部分高级特性尚未迁移）
- ⚠️ 测试覆盖（未达到 V1 的测试水平）
- ℹ️ V1 `GPUModelRunner` 仍是默认的生产 runner

## 两个新特性对比

| | DBO | MRV2 |
|------|-----|------|
| **目标场景** | MoE 模型（DeepSeek V2/V3） | 所有模型 |
| **优化维度** | 通信-计算重叠 | 全面架构改进 |
| **成熟度** | 实验性 | 开发中 |
| **依赖** | DP+EP + DeepEP | 无特殊依赖 |
| **是否默认** | 否（需 `--enable-dbo`） | 否 |
| **适用规模** | 2+ GPU DP 部署 | 任意 |
