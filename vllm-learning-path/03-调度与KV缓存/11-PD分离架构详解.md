## 二、请求入口到 P 节点调度

```mermaid
sequenceDiagram
    participant U as 👤 用户
    participant AL as AsyncLLM
    participant IP as InputProcessor
    participant LB as DPLBAsyncMPClient
    participant DC as DPCoordinator
    participant P_EC as P-EngineCoreProc
    participant P_S as P-Scheduler
    participant P_KV as P-KVConnector(Scheduler)

    U->>AL: POST /v1/completions
    AL->>IP: 分词 + 构造 EngineCoreRequest
    IP-->>AL: EngineCoreRequest

    Note over AL,LB: DP 负载均衡决策

    AL->>LB: get_core_engine_for_request()
    LB->>LB: 计算 min(waiting*4 + running)
    LB->>DC: 查询各引擎负载统计
    DC-->>LB: [(waiting, running), ...]
    LB-->>AL: chosen_engine (P-0)

    AL->>LB: add_request_async(request)
    LB->>P_EC: ZMQ ADD message (EngineCoreRequest)

    P_EC->>P_EC: process_input_sockets()
    P_EC->>P_EC: preprocess_add_request(request)
    P_EC->>P_S: scheduler.add_request(req)

    alt KV Transfer (远程 Prefill)
        P_S->>P_KV: get_num_new_matched_tokens(req)
        Note over P_KV: kv_transfer_params.do_remote_prefill?<br/>查远程 D 有哪些现成 KV blocks
        P_KV-->>P_S: (num_external_tokens, is_async)
    end

    P_S->>P_S: 加入 waiting queue
    Note over P_S: 等待下次 schedule() 调用
```

## 三、P 侧 Prefill 调度与 KV 传输

```mermaid
sequenceDiagram
    participant P_EC as P-EngineCoreProc
    participant P_S as P-Scheduler
    participant P_KVM as P-KVCacheManager
    participant P_KVS as P-KVConnector(Scheduler)
    participant P_W as P-Worker(GPU)
    participant P_KVW as P-KVConnector(Worker)
    participant D_KVW as D-KVConnector(Worker)

    P_EC->>P_S: schedule(throttle_prefills=False)
    P_S->>P_S: 从 waiting queue 取请求
    P_S->>P_KVS: get_num_new_matched_tokens(req)
    P_KVS-->>P_S: (matched_tokens, async)

    P_S->>P_KVM: allocate_blocks(req, num_tokens)
    P_KVM-->>P_S: KVCacheBlocks

    P_S->>P_KVS: update_state_after_alloc(req, blocks)
    Note over P_KVS: 对于远程 Prefill 请求：<br/>注册 _reqs_need_recv<br/>准备拉取远程 KV blocks

    P_S->>P_KVS: build_connector_meta(scheduler_output)
    P_KVS-->>P_S: NixlConnectorMetadata

    P_S-->>P_EC: SchedulerOutput (含 kv_connector_metadata)

    P_EC->>P_W: execute_model(scheduler_output)
    P_W->>P_KVW: bind_connector_metadata(meta)
    P_W->>P_KVW: start_load_kv(forward_context)

    alt Pull 模式 (READ)
        P_KVW->>D_KVW: NIXL RDMA READ<br/>从 D 的 GPU 读取 KV blocks
        D_KVW-->>P_KVW: KV data 传输完成
    else Push 模式 (WRITE)
        D_KVW->>P_KVW: NIXL 注册通知<br/>告知 D 侧内存地址
        P_KVW->>D_KVW: NIXL RDMA WRITE<br/>写入 KV blocks 到 D 侧
    end

    P_KVW->>P_KVW: wait_for_layer_load(layer_name)
    Note over P_KVW: 逐层等待 KV 加载完成<br/>支持流水线：load layer_i<br/>while compute layer_(i-1)

    P_W->>P_W: Model Forward (Prefill)
    P_W->>P_KVW: wait_for_save()
    Note over P_KVW: 等待异步保存完成<br/>(如果使用 host buffer)

    P_W-->>P_EC: ModelRunnerOutput
    P_EC->>P_S: update_from_output(scheduler_output, output)
    P_S->>P_S: 更新请求状态

    alt Prefill 完成
        P_S->>P_KVS: request_finished(req, block_ids)
        P_KVS-->>P_S: (delay_free, kv_transfer_params)
        Note over P_KVS: 返回 kv_transfer_params：<br/>do_remote_prefill=True<br/>remote_block_ids=[...]<br/>remote_engine_id=...<br/>remote_host / remote_port
    end
```

### D 侧 DP 选择（Decode 阶段）

D 侧节点的选择有两种方式：

1. **显式指定**：P 完成 Prefill 后，`kv_transfer_params` 中携带目标 D 的 `remote_engine_id`，直接路由到该 D 引擎
2. **负载均衡**：如果是新 Decode 请求（没有关联的 P），由 `DPLBAsyncMPClient` 使用同样算法动态选择

## 八、完整生命周期时序图

```mermaid
sequenceDiagram
    participant User as 👤 用户
    participant FE as Frontend/AsyncLLM
    participant DC as DPCoordinator
    participant P as P-EngineCore<br/>(kv_producer)
    participant D as D-EngineCore<br/>(kv_consumer)
    participant NIXL as NIXL/RDMA

    %% 阶段 1: 请求入口
    User->>FE: 发送请求
    FE->>FE: InputProcessor 分词
    FE->>FE: LB 选择 P 节点

    %% 阶段 2: P 节点调度 + Prefill
    FE->>P: add_request()
    P->>P: Scheduler.schedule()
    P->>P: KVCacheManager.allocate()
    P->>P: GPU Prefill Forward

    %% 阶段 3: Prefill 完成，构造 KV 传输参数
    P->>P: request_finished()
    Note over P: 生成 kv_transfer_params<br/>remote_engine_id, remote_block_ids

    P-->>FE: EngineCoreOutputs<br/>(含 kv_transfer_params)

    %% 阶段 4: 请求转发到 D 节点
    FE->>FE: 根据 kv_transfer_params<br/>确定目标 D 节点
    FE->>D: add_request(带 kv_transfer_params)

    %% 阶段 5: D 侧握手 + KV 传输
    D->>D: Scheduler 读取 kv_transfer_params
    D->>D: get_num_new_matched_tokens()
    D->>D: allocate_blocks()
    D->>D: update_state_after_alloc()

    D->>NIXL: 通过侧通道获取 P 的 Agent Metadata
    NIXL-->>D: NixlAgentMetadata

    D->>NIXL: start_load_kv() → NIXL RDMA READ
    NIXL->>P: 从 P GPU 读取 KV
    P-->>NIXL: KV Data Blocks
    NIXL-->>D: KV 写入 D GPU

    D->>D: wait_for_layer_load()

    %% 阶段 6: D 节点 Decode
    loop 每个 Decode Step
        D->>D: Scheduler.schedule()
        D->>D: GPU Decode Forward (1 token)
        D->>D: update_from_output()
        D-->>FE: EngineCoreOutputs (token)
        FE-->>User: 流式返回 token
    end

    %% 阶段 7: 完成
    D->>NIXL: 心跳维持 KV Block 租约
    Note over D: 请求完成后<br/>通过心跳通知 P 释放 blocks
    D-->>FE: finish_reason = STOP
    FE-->>User: [DONE]
```

## 十、核心数据流总结

```mermaid

    subgraph P_SIDE["⚡ Prefill 侧 (kv_producer)"]
        A["① 请求到达"] --> B["② Prefill 调度"]

        I --> J["⑩ start_load_kv()<br/>NIXL RDMA READ/WRITE"]

    style P_SIDE fill:#e3f2fd,stroke:#1565c0
    style TRANSIT fill:#fff3e0,stroke:#e65100
    style D_SIDE fill:#e8f5e9,stroke:#2e7d32
```

> **关键设计原则**：
> 1. **P/D 分离**：Prefill 是高计算量（O(n²)）一次处理全部 prompt tokens；Decode 是低计算量（O(n)）逐个生成 token。分离后可以独立扩缩容。
> 2. **KV Connector 抽象**：Scheduler 侧管理元数据和调度决策，Worker 侧执行实际的 KV 传输（RDMA/NIXL/Mooncake 等）。
> 3. **异步传输**：KV 加载可以与 Model Forward 流水线化（`start_load_kv` → `wait_for_layer_load`），隐藏网络延迟。
> 4. **DP 负载均衡**：通过 `DPCoordinator` 实时收集各引擎负载，`DPLBAsyncMPClient` 基于 `waiting×4 + running` 打分选择最优引擎。
> 5. **MoE EP 特殊处理**：DPEngineCoreProc 增加了 Prefill 对齐（`prefill_schedule_interval`）和 Wave 同步（AllReduce）机制。
