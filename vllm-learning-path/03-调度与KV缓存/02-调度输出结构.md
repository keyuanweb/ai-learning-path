# 02 · 调度输出结构

**源码**：[`code/vllm/vllm/v1/core/sched/output.py`](../../code/vllm/vllm/v1/core/sched/output.py)

## `SchedulerOutput`

一个 dataclass，包含一步调度的完整结果。Executor 根据它构建 GPU 输入。

| 字段 | 类型 | 说明 |
|------|------|------|
| `scheduled_new_reqs` | `list[NewRequestData]` | 本步新加入的请求的全量数据 |
| `scheduled_cached_reqs` | `CachedRequestData` | 已在运行的请求的本步增量 |
| `num_scheduled_tokens` | `dict[str, int]` | 每个请求本步算几个 token |
| `total_num_scheduled_tokens` | `int` | 本步总共算多少 token（batch input size） |
| `scheduled_spec_decode_tokens` | `dict[str, list[int]]` | 投机解码的 draft token IDs |
| `scheduled_encoder_inputs` | `dict[str, list[int]]` | 多模态 encoder 需要处理的输入 |
| `num_common_prefix_blocks` | `list[int]` | 公共前缀块数（cascade attention 优化） |
| `preempted_req_ids` | `set[str]` | 本步被抢占的请求 |
| `finished_req_ids` | `set[str]` | 本步完成的请求 |
| `has_structured_output_requests` | `bool` | 本步被调度的请求中是否有使用结构化输出的 |
| `pending_structured_output_tokens` | `bool` | 被调度请求是否已具备语法 bitmask 计算所需的全部输出 token |

> 注：`structured_output_request_ids` 和 `grammar_bitmask` 是 `GrammarOutput`（同文件）的字段，由 `get_grammar_bitmask()` 返回，不是 `SchedulerOutput` 的字段。

## `NewRequestData` — 新请求的完整信息

```python
class NewRequestData(msgspec.Struct):
    req_id: str
    prompt_token_ids: list[int]      # 全量 prompt（可能部分已被 prefix cache 覆盖）
    mm_features: list[...]            # 多模态特征
    sampling_params: SamplingParams
    pooling_params: PoolingParams | None
    block_ids: list[int]              # 分配的 KV 块号列表
    num_computed_tokens: int          # 已计算（含 prefix cache 命中数量）
    num_tokens_with_spec: int         # 含投机 token 的总数
    lora_request: LoRARequest | None
    ecc_type: EncoderCacheType | None # encoder cache 类型
```

## `CachedRequestData` — 旧请求的增量

```python
class CachedRequestData(msgspec.Struct):
    req_ids: list[str]
    resumed_req_ids: list[str]          # 抢占后恢复的请求 IDs
    new_token_ids: list[list[int]]      # 每请求新增的 token IDs
    new_block_ids: list[int] | None     # 每请求新增的 KV 块号
    num_computed_tokens: list[int]      # 每请求当前 computed 位置
    num_output_tokens: list[int]        # 每请求已生成的 output token 数
    num_output_placeholders: list[int]  # 每请求的投机占位 token 数
```

## 新旧请求的数据差异 — 为什么分开

| 属性 | 新请求 (`NewRequestData`) | 旧请求 (`CachedRequestData`) |
|------|--------------------------|------------------------------|
| prompt token IDs | 全量 | 不需要（已在 GPUModelRunner 的状态中） |
| KV block IDs | 全量（首轮分配） | 仅增量（追加的块） |
| 数据量 | O(prompt_len) | O(1)（decode 时只需 1 个 token） |

分开的原因是**减少序列化开销**：旧请求数据量极小，可以快速跨进程传递。

## 阅读重点

- 理解「新请求」和「旧请求」（cached）的数据差异 —— 每次只有新请求才传全量 prompt
- `block_ids` 和 `new_block_ids` 是 KV 缓存的逻辑块号，后面 Worker 用它们寻址物理显存
- `num_common_prefix_blocks` 是 cascade attention 优化的关键参数
