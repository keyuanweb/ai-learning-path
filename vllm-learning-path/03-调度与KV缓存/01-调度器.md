## V1 统一调度的核心思想

V0 有显式的 prefill 阶段和 decode 阶段。V1 消除了这个区别。

每个 Request 有 `num_computed_tokens`（已计算）和 `num_tokens_with_spec`（总 token 数，含投机 token）。调度器的唯一任务是**让前者追上后者**。

这统一地处理了：
- **纯 prefill**：差值 1000（一次追完或分 chunk）
- **chunked prefill**：差值 800（本步追一部分，下步继续追）
- **decode**：差值 1（每次生成一个 token）
- **speculative decoding**：差值 5（一次验证 5 个 draft token）

## `Scheduler` 的关键状态

| 属性 | 说明 |
|------|------|
| `self.running: list[Request]` | 正在执行的请求（调度器持有） |
| `self.waiting: RequestQueue` | 等待队列（支持 FCFS 或 priority 两种排队策略） |
| `self.kv_cache_manager: KVCacheManager` | KV 缓存管理器（分配/释放/prefix cache 查询） |
| `self.token_budget: int` | 每步最多计算几个 token（`max_num_batched_tokens`） |
| `self.max_num_seqs: int` | 同时 running 的最多请求数 |

## `schedule()` 算法（三阶段）

```python
def schedule(self) -> SchedulerOutput:
    # 阶段 1：处理 RUNNING 请求
    for req in self.running:
        num_new = req.num_tokens_with_spec - req.num_computed_tokens
        # 受 token_budget 约束：如果预算不够，chunked prefill
        scheduled = min(num_new, remaining_token_budget)
        # 受 max_model_len 约束：不能超过模型最大长度

    # 阶段 2：处理 WAITING 请求
    for req in self.waiting:
        # 检查 prefix cache 命中
        num_cached = self.kv_cache_manager.get_computed_blocks(req)
        if num_cached > 0:
            # 命中！这些 token 不需要重新计算

        # KV 块分配
        if self.kv_cache_manager.allocate_slots(req, num_new_tokens):
            # 分配成功，加入 running
            self.running.append(req)
        else:
            # KV 缓存不够，考虑抢占低优先级请求
            self._preempt_lowest_priority()

        # 受 max_num_seqs 约束
        if len(self.running) >= self.max_num_seqs:
            break

    # 阶段 3：处理 encoder 输入（多模态）
    self._try_schedule_encoder_inputs(...)

    # 组装 SchedulerOutput
    return SchedulerOutput(
        scheduled_new_reqs=...,
        scheduled_cached_reqs=...,
        num_scheduled_tokens=...,
        finished_req_ids=...,
        preempted_req_ids=...,
    )
```

## 抢占（Preemption）

当 KV 缓存满时，调度器会**抢占**（preempt）一个低优先级的 running 请求：
1. 找到一个优先级最低且可抢占的请求
2. 释放它的所有 KV 块（`kv_cache_manager.free(req)`）
3. 重置 `num_computed_tokens = 0`（下次重调度时需要全部重算）
4. 移回 `waiting` 队列
5. 发送 `PREEMPTED` 事件

抢占的代价是「被抢占的请求已经算过的 token 全部白算」——所以只发生在 KV 缓存严重不足时。
