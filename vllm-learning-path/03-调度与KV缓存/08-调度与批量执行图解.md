## 一、总体流程：一个 step 的全景图

vLLM V1 的推理过程是一个**紧循环**（tight loop），每一步经历「调度 → 执行 → 采样 → 更新」四个阶段：

```mermaid
flowchart TB
    subgraph engine["EngineCore.step() 推理紧循环"]
        direction TB
        S["🔵 阶段1: Scheduler.schedule()<br/>决定本步算哪些请求、各算几个 token"]
        E["🟢 阶段2: ModelRunner.execute_model()<br/>构建 InputBatch → 模型前向"]
        G["🟡 语法约束: get_grammar_bitmask()<br/>结构化输出 token 合法性检查"]
        U["🔴 阶段3: update_from_output()<br/>更新请求状态、检查 stop、释放 KV 块"]
        S --> E --> G --> U -->|下一步| S
    end

    subgraph queues["请求队列"]
        W["waiting 队列<br/>待调度的新请求/被抢占请求"]
        R["running 列表<br/>正在推理的请求"]
    end

    W -->|"新请求被调度"| S
    R -->|"继续调度"| S
    U -->|"完成的请求退出"| R
    U -->|"结果输出"| O["EngineCoreOutputs<br/>→ 返回给前端"]
```

### 核心数据结构流转

```mermaid
flowchart LR
    subgraph step["一步内的数据流"]
        direction LR
        so["SchedulerOutput"]
        ib["InputBatch"]
        mo["ModelRunnerOutput"]
        eco["EngineCoreOutputs"]
    end

    so -->|"ModelRunner<br/>prepare_inputs()"| ib
    ib -->|"model.forward()<br/>+ sample_tokens()"| mo
    mo -->|"Scheduler<br/>update_from_output()"| eco
```

**关键点**：`SchedulerOutput` 是调度和执行之间的契约——调度器告诉执行器「算什么」，执行器返回「算出了什么」。

## 二、调度逻辑详解（三阶段算法）

### 2.1 统一调度模型

V1 不区分 prefill/decode 阶段。每个请求的核心状态只有两个计数器：

```mermaid
flowchart LR
    nct["num_computed_tokens<br/>已计算的 token 数"]
    nts["num_tokens_with_spec<br/>总 token 数（含投机 token）"]
    gap["差值 = 本步需要计算的 token 数"]

    nct -->|"追赶"| nts
    nct --> gap
    nts --> gap
```

| 场景 | num_computed_tokens | num_tokens_with_spec | 差值（本步要算） |
|------|---------------------|----------------------|:---:|
| 新请求 prefill | 0 | 1000 | 1000 |
| chunked prefill | 200 | 1000 | ≤800 (被 token_budget 截断) |
| decode | 999 | 1000 | 1 |
| speculative decoding | 990 | 1000 | 10 (5 bonus + 5 draft) |

### 2.2 三阶段调度算法

```mermaid
flowchart TB
    subgraph schedule["schedule() 算法"]
        direction TB
        start["开始: token_budget = max_num_scheduled_tokens"]

        subgraph p1["阶段1: 处理 RUNNING 请求"]
            p1a["遍历 self.running 列表"]
            p1b["计算 num_new = num_tokens_with_spec<br/>- num_computed_tokens"]
            p1c["约束: min(num_new, token_budget, max_model_len)"]
            p1d["KV 块分配: allocate_slots()"]
            p1e{"分配成功?"}
            p1yes["加入 scheduled_running_reqs<br/>token_budget -= num_new"]
            p1no["抢占低优先级请求<br/>释放其 KV 块<br/>移回 waiting 队列"]
        end

        subgraph p2["阶段2: 处理 WAITING 请求"]
            p2a["检查 max_num_seqs 约束"]
            p2b["Prefix Cache 查询<br/>get_computed_blocks()"]
            p2c["KV 块分配: allocate_slots()"]
            p2d{"分配成功?"}
            p2yes["请求移入 running 列表<br/>加入 scheduled_new_reqs"]
            p2no["跳出: 本步不再调度新请求"]
        end

        subgraph p3["阶段3: 组装输出"]
            p3a["构造 NewRequestData<br/>（新请求全量数据）"]
            p3b["构造 CachedRequestData<br/>（旧请求增量数据）"]
            p3c["计算公共前缀块数<br/>（cascade attention 优化）"]
            p3d["返回 SchedulerOutput"]
        end
    end

    start --> p1a --> p1b --> p1c --> p1d --> p1e
    p1e -->|是| p1yes --> p1a
    p1e -->|否| p1no --> p1a
    p1a -->|"遍历完毕或 token_budget=0"| p2a
    p2a --> p2b --> p2c --> p2d
    p2d -->|是| p2yes --> p2a
    p2d -->|否| p2no --> p3a
    p3a --> p3b --> p3c --> p3d
```

### 2.3 Token Budget 分配（气泡图）

每步有 `max_num_scheduled_tokens`（默认= `max_num_batched_tokens`，如 16384）。调度器的任务是把这笔「预算」分配给各个请求：

```mermaid
flowchart TB
    budget["🟡 Token Budget 总量: 16384 tokens/step"]

    budget --> decode_group

    subgraph decode_group["Decode 请求（轻量，每次 1 token）"]
        d1["Req-A: 1 token"]
        d2["Req-B: 1 token"]
        d3["..."]
        d500["Req-第500个: 1 token"]
    end

    budget --> prefill_group

    subgraph prefill_group["Chunked Prefill 请求（较重，几十~几百 token）"]
        p1["Req-C: 256 tokens<br/>💡 长 prompt 被切成多个 chunk"]
        p2["Req-D: 512 tokens"]
    end

    budget --> remaining

    subgraph remaining["剩余预算"]
        rest["≈ 15626 tokens 未使用<br/>可继续容纳 prefill 请求<br/>或更多 decode 请求"]
        rest_style[" "]
    end

    decode_group -->|"小计: ~500 tokens (3%)"| consumed["已分配: ~758 tokens (4.6%)"]
    prefill_group -->|"小计: ~768 tokens (4.7%)"| consumed

    style budget fill:#fff3cd,stroke:#ffc107,stroke-width:3px
    style decode_group fill:#d1ecf1,stroke:#0c5460
    style prefill_group fill:#d4edda,stroke:#155724
    style remaining fill:#f8f9fa,stroke:#6c757d,stroke-dasharray: 5 5
    style consumed fill:#f1f1f1,stroke:#999
```

> **💡 图解要点**：Decode 请求每次只消耗 1 token，即使 500 个并发也只占预算的 ~3%。真正的预算消耗大户是 **Chunked Prefill**——长 prompt 被切分为多个 chunk，每步消耗一部分预算。当预算用尽时，新 prefill 请求必须等待下一轮。

**核心要点**：
- **Decode 请求**：每次只消耗 1 token（生成下一个 token），极轻量
- **Chunked prefill**：长 prompt 被切成多个 chunk，每步消耗一部分预算
- **预算用尽 → 停止调度**：哪怕 waiting 队列还有请求，也不能在本步调度
- **Decode 优先于 prefill**：先处理 running 中的 decode（阶段1），再调度新 prefill（阶段2）

### 2.4 Chunked Prefill 的 token 预算切分

当 `num_new_tokens > token_budget` 且启用 chunked prefill 时：

```mermaid
flowchart LR
    prompt["Prompt: 8000 tokens"]
    chunk1["Step 1<br/>token_budget 允许<br/>→ 调度 2048 tokens"]
    chunk2["Step 2<br/>→ 调度 2048 tokens"]
    chunk3["Step 3<br/>→ 调度 2048 tokens"]
    chunk4["Step 4<br/>→ 调度 1856 tokens<br/>prefill 完成"]
    decode["Step 5+<br/>→ decode 1 token/step"]

    prompt --> chunk1 --> chunk2 --> chunk3 --> chunk4 --> decode
```

如果**禁用** chunked prefill，长 prompt 无法拆分，会直接 `break` 跳过（等待更多预算释放）。

## 三、KV 缓存块分配流程

### 3.1 Block Pool 与分配逻辑

KV 缓存以 **Block** 为单位管理（默认 block_size=16 tokens）。Block Pool 是所有请求共享的物理块池：

```mermaid
flowchart TB
    subgraph pool["GPU Block Pool"]
        direction LR
        b0["Block 0<br/>🟢 使用中"]
        b1["Block 1<br/>🟢 使用中"]
        b2["Block 2<br/>⚪ 空闲"]
        b3["Block 3<br/>⚪ 空闲"]
        b4["Block 4<br/>🟡 缓存中<br/>（prefix cache）"]
        b5["Block 5<br/>🟢 使用中"]
        b6["Block 6<br/>⚪ 空闲"]
        b7["Block 7<br/>⚪ 空闲"]
        bdots["..."]
    end

    subgraph free_q["Free Block Queue"]
        fq["[2, 3, 6, 7, ...] — 空闲块优先从队头取"]
    end

    subgraph hash_cache["Block Hash → Block Map<br/>Prefix Cache 索引"]
        hc["hash_abc → Block 4<br/>hash_def → Block 1<br/>..."]
    end

    free_q -->|"allocate_slots() 从队头取"| pool
    hash_cache -->|"get_computed_blocks() 查询命中"| pool
```

### 3.2 Prefix Cache 命中流程

```mermaid
flowchart TB
    req["新请求: prompt = 'The capital of France is Paris'"]
    hash["计算 prompt 的 block hashes<br/>block_hashes = [H1, H2, H3, H4]"]
    query["get_computed_blocks(request)<br/>查询 block hash 是否在缓存中"]

    subgraph hit["命中场景"]
        h1["H1 → Block 4 ✓ 命中"]
        h2["H2 → Block 1 ✓ 命中"]
        h3["H3 → 未命中 ✗"]
        h4["H4 → 未命中 ✗"]
        result["result: num_computed_tokens = 32<br/>（前 2 个 block = 32 token 已缓存）"]
    end

    skip["跳过前 32 个 token 的计算<br/>只需计算 H3, H4 对应的 token"]

    req --> hash --> query --> hit --> skip
```

**意义**：Prefix Cache 让相同前缀的请求共享 KV 缓存块，避免重复计算。系统提示词固定的场景下效果显著。

### 3.3 抢占（Preemption）机制

当 KV 缓存池不足以分配新请求所需的 block 时：

```mermaid
flowchart TB
    need["Req-A 需要 10 个新 block"]
    check{"free block queue<br/>数量足够?"}

    enough["直接从 free queue 分配<br/>→ 请求正常调度"]
    not_enough["block 不够"]

    subgraph preempt["抢占流程"]
        p1["从 running 列表中<br/>选出优先级最低的请求 Req-X"]
        p2["释放 Req-X 的所有 KV block<br/>（归还 free queue）"]
        p3["Req-X.num_computed_tokens = 0<br/>（下次重调度从头算起）"]
        p4["Req-X 移回 waiting 队列<br/>status = PREEMPTED"]
    end

    retry{"Block 够了吗?"}
    success["Req-A 分配成功<br/>→ 正常调度"]
    fail["还是不够<br/>→ Req-A 本轮无法调度"]

    need --> check
    check -->|够| enough
    check -->|不够| not_enough --> preempt --> retry
    retry -->|够| success
    retry -->|不够| fail
```

**代价**：被抢占请求的所有已计算 KV 全部丢失——下次从 0 重新 prefill。这是 kv cache 严重不足时的最后手段。

## 四、批量推理执行原理

### 4.1 从 SchedulerOutput 到 InputBatch

调度器产出 `SchedulerOutput` 后，`GPUModelRunner.execute_model()` 将其转换为模型可以消费的 InputBatch：

```mermaid
flowchart TB
    subgraph so["SchedulerOutput（调度结果）"]
        s1["num_scheduled_tokens<br/>{req_a: 1, req_b: 1, req_c: 256}"]
        s2["scheduled_new_reqs<br/>[NewRequestData, ...]"]
        s3["scheduled_cached_reqs<br/>CachedRequestData"]
        s4["scheduled_spec_decode_tokens<br/>{req_a: [d1,d2,d3], ...}"]
    end

    subgraph ib["InputBatch（模型输入）"]
        i1["input_ids<br/>[token_a, token_b, token_c1...c256]<br/>shape: [258] ← 所有请求的 token 平铺"]
        i2["positions<br/>[999, 500, 0, 1, ..., 255]<br/>shape: [258] ← 每个 token 在序列中的位置"]
        i3["query_start_loc<br/>[0, 1, 2, 258]<br/>shape: [num_reqs+1] ← 累加偏移"]
        i4["seq_lens<br/>[1000, 501, 256]<br/>shape: [num_reqs] ← 各序列当前长度"]
        i5["block_tables<br/>[[B0,B1,...], [B3,B5,...], ...]<br/>shape: [num_reqs, max_blocks]"]

    s3 --> i5
```

### 4.3 单 Token vs 多 Token 的 Batch 形态

不同请求在同一 batch 中可以有不同的 query 长度——这就是 V1 混合 batch 的核心能力：

```mermaid
flowchart TB
    subgraph batch["一个混合 Batch — 不同请求的 query 长度各不相同"]
        direction LR
        subgraph decode_reqs["Decode 请求（query_len=1）"]
            d1["Req-A<br/>1 token"]
            d2["Req-B<br/>1 token"]
            d3["Req-C<br/>1 token"]
            d4["..."]
            d5["Req-N<br/>1 token"]
        end
        subgraph prefill_req["Chunked Prefill（query_len=512）"]
            p1["Req-P<br/>512 tokens"]
        end
    end

    batch --> qsl

    subgraph qsl["query_start_loc 划分各请求范围"]
        loc["[0, 1, 2, 3, ..., N, N+512]<br/>↑ Req-A 的 1 个 token 在 [0,1)<br/>↑ Req-B 的 1 个 token 在 [1,2)<br/>...<br/>↑ Req-P 的 512 个 token 在 [N, N+512)"]
    end

    style decode_reqs fill:#d1ecf1,stroke:#0c5460
    style prefill_req fill:#d4edda,stroke:#155724
    style batch fill:#f8f9fa,stroke:#999,stroke-dasharray: 5 5
```

**注意**：decode 请求的 query 长度 = 1（只算最后一个 token），而 chunked prefill 请求的 query 长度 = 本步分配的 chunk 大小。Attention kernel 通过 `query_start_loc`（累加偏移量数组）知道每个请求的 token 从哪开始、到哪结束。

### 4.4 Attention 与 KV Cache 写入

```mermaid
flowchart TB
    subgraph attn_flow["每个 token 的 Attention 计算"]
        q["Query: 当前 token<br/>（从 input_ids 取出）"]
        k["Key/Value: 通过 block_table<br/>找到序列所有历史 token 的 KV"]
        attn["Attention 计算<br/>Q · K^T → softmax → ·V"]
        write["当前 token 的 KV<br/>写入 slot_mapping 指向的 block slot"]
    end

    subgraph block_map["Block Table 映射"]
        bt["req.block_table = [Block10, Block15, Block22, Block3]"]
        phys["物理 KV cache tensor 寻址<br/>Block10 → offset 10×block_size<br/>Block15 → offset 15×block_size<br/>..."]
    end

    q --> attn
    k --> attn
    bt --> phys --> k
    attn --> write --> phys
```

**关键设计**：Block Table 提供虚拟到物理的映射，使 KV cache 块可以不连续分配。这是 PagedAttention 的核心——像操作系统的虚拟内存页表一样管理 KV 缓存。

### 4.5 CUDA Graph 加速

vLLM 通过预录制 CUDA Graph 消除 kernel launch overhead：

```mermaid
flowchart TB
    subgraph warmup["Warmup 阶段（启动时）"]
        w1["为不同 batch 配置录制 CUDA Graph<br/>（batch_size=1,2,4,...,max）"]
        w2["每个 graph 内包含:<br/>模型所有层的 forward kernel<br/>+ 采样 kernel"]
    end

    subgraph runtime["运行时"]
        r1{"当前 batch 有<br/>匹配的 graph?"}
        r2["直接 replay graph<br/>↓ 单次 CUDA API 调用<br/>↓ 所有 kernel 自动执行"]
        r3["Eager 模式<br/>逐层调用 model forward"]
    end

    warmup --> runtime
    r1 -->|"是（大部分情况）"| r2
    r1 -->|"否（罕见 batch 配置）"| r3
```

CUDA Graph 的前提是 batch 的 **token 总数和请求数** 必须与录制时一致。对于「全 decode」（每个请求 1 token）的场景，graph 录制很容易覆盖；对于混合 batch 中包含变长 chunked prefill 的场景，可能需要 eager 或 PIECEWISE 模式。

## 五、完整体验：一个请求从进入到产出

以一次 decode 步骤为例，跟踪一个 token 的完整旅程：

```mermaid
sequenceDiagram
    participant U as User/前端
    participant S as Scheduler
    participant MR as GPUModelRunner
    participant M as Model (GPU)
    participant KV as KV Cache

    Note over S: === 上一次 step 结束后 ===
    S->>S: update_from_output()<br/>Req.num_computed_tokens += 1<br/>（追上了一个 token）

    Note over S: === 新一轮 step 开始 ===
    S->>S: schedule()<br/>检查 running 列表中的 Req<br/>num_new = 1 (decode)
    S->>KV: allocate_slots(Req, num_new=1)<br/>分配 1 个 block slot（若当前 block 满了则新分配 block）
    KV-->>S: new_blocks (slot 位置)
    S->>S: 组装 SchedulerOutput<br/>num_scheduled_tokens[req_id] = 1

    S->>MR: execute_model(scheduler_output)
    MR->>MR: prepare_inputs()<br/>input_ids = [last_token_id]<br/>positions = [999]
    MR->>MR: prepare_attn()<br/>block_table → slot_mappings
    MR->>M: model.forward(input_ids, positions, attn_metadata)
    M->>KV: 读取 KV cache（通过 block_table 寻址）
    M->>KV: 写入新 KV（通过 slot_mappings 寻址）
    M-->>MR: hidden_states → logits
    MR->>MR: sample_tokens()<br/>logits → sampled_token_id
    MR-->>S: ModelRunnerOutput(sampled_token_ids=[3042])

    S->>S: update_from_output(scheduler_output, model_output)<br/>Req.append_output_token_ids(3042)<br/>检查 stop 条件
    S-->>U: EngineCoreOutput(new_token_ids=[3042])
```

## 六、关键概念速查

| 概念 | 一句话解释 | 管理方 |
|------|-----------|--------|
| **token_budget** | 每步最多算多少 token（如 16384），限制 batch 总计算量 | Scheduler |
| **max_num_seqs** | 最多同时 running 多少请求（如 256），限制并发数 | Scheduler |
| **chunked prefill** | 长 prompt 分多步计算，避免单步计算量过大 | Scheduler |
| **prefix cache** | 相同 prompt 前缀共享 KV block，避免重复计算 | KVCacheManager |
| **block_table** | 每个请求的虚拟块号→物理块号的映射表 | BlockTables (Worker) |
| **slot_mapping** | 每个 token 的 KV 写入位置（block_id × block_size + offset） | ModelRunner |
| **query_start_loc** | 累加偏移数组，Attention kernel 用此划分 batch 中各请求的 token 范围 | InputBatch |
| **抢占** | KV cache 不足时踢出低优先级请求，其已算 KV 全部丢失 | Scheduler |
| **CUDA Graph** | 预录制 kernel 序列，运行时一次 API 调用重放，消除 launch overhead | CUDAGraphManager |

## 阅读重点

- 理解「统一调度模型」：`num_computed_tokens` 追 `num_tokens_with_spec`，一个模型覆盖所有场景
- 跟一遍三阶段调度：running → waiting → assemble
- 记住 `token_budget` 和 `max_num_seqs` 是两个独立约束
- 理解 InputBatch 的 flat 布局：所有请求的 token 合并为一个一维数组，通过 `query_start_loc` 划分边界
- 知道 block_table 是实现 PagedAttention 的核心：虚拟块号→物理块号映射
- CUDA Graph 是性能关键：预录制避免 kernel launch overhead
