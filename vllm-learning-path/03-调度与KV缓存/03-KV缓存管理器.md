# 03 · KV 缓存管理器

**源码**：[`code/vllm/vllm/v1/core/kv_cache_manager.py`](../../code/vllm/vllm/v1/core/kv_cache_manager.py)

## 职责

`KVCacheManager` 是对调度器暴露的 KV 缓存接口。它把底层 KV 块的分配/释放/查找封装为简洁的方法，隐藏了「多种 KV 缓存类型」「prefix cache 逻辑」「块池管理」的复杂性。

## 对调度器暴露的接口

| 方法 | 参数 | 说明 |
|------|------|------|
| `allocate_slots(request, num_new_tokens)` | 请求 + 需要几个 token 的 slot | 给请求的 N 个新 token 分配 KV 块。返回 `KVCacheBlocks`（含着块号列表），分配失败返回 None |
| `get_computed_blocks(request)` | 请求 | 检查 prefix cache 命中。返回已存在的 `KVCacheBlocks`，值为 None 表示无命中 |
| `free(request)` | 请求 | 释放请求的全部 KV 块，递减块引用计数 |
| `get_blocks(request)` | 请求 | 获取请求当前持有的块列表（用于构建 block table） |
| `evict_blocks(block_ids)` | 块 ID 集合 | 按块号从 prefix cache 驱逐指定块 |

## Prefix Cache 的工作原理

1. **哈希计算**：每个 KV 块的内容（由 `token_ids` 和 `block_id` 决定）产生一个哈希值
2. **哈希 → 块映射**：`BlockHashToBlockMap(hash → set[block_id])` 存储哈希到 KV 块的映射
3. **命中查询**：请求 B 的 prompt prefix token sequence 产生哈希序列，逐块在 BlockHashToBlockMap 中查找
4. **命中后复用**：`get_computed_blocks()` 返回匹配到的 KV 块列表，调度器将 `num_computed_tokens` 跳过这些已计算部分
5. **引用计数**：当块被多个请求共享时，`ref_count(+1)`；请求完成时 `ref_count(-1)`，降到 0 时块回收到空闲队列

这就是为什么 prefix cache 在「多请求共享相同系统提示」的场景下特别有效——第二个请求的 prompt prefix 和第一个相同，哈希完全匹配，直接复用 KV 块。

## 内部委托

`KVCacheManager` 是 facade 模式——它把请求路由到正确的 `SingleTypeKVCacheManager`（通过 `KVCacheCoordinator`）：

- 不同 attention 类型（FullAttention vs MLA vs SlidingWindow）有独立的 `SingleTypeKVCacheManager`
- 每种类型有自己的 `BlockPool` 和 `FreeKVCacheBlockQueue`
- `KVCacheManager` 根据 request 的 kv_cache_group 选择对应的 manager

## 阅读重点

- 理解 `allocate_slots`（为新 token 分配 KV 空间）和 `get_computed_blocks`（prefix cache 命中查询）的语义

- 知道 KVCacheManager 是 facade，底层按 attention 类型分治管理
