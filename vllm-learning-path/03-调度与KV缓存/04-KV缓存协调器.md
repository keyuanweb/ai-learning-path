# 04 · KV 缓存协调器与块池

## KVCacheCoordinator

**源码**：[`code/vllm/vllm/v1/core/kv_cache_coordinator.py`](../../code/vllm/vllm/v1/core/kv_cache_coordinator.py)

这是 KV 块的实际管理者。核心数据结构：

### BlockPool — 所有 KV 块的大池子

```python
class BlockPool:
    blocks: list[KVCacheBlock]       # 所有块
    free_blocks: FreeKVCacheBlockQueue  # 空闲块队列
    prefix_cache: BlockHashToBlockMap    # prefix cache 的哈希→块映射
```

### KVCacheBlock — 单个 KV 块

```python
class KVCacheBlock:
    block_id: int
    ref_count: int       # 被几个请求引用（prefix cache 时 >1）
    block_hash: int      # 内容的哈希值
    prev_block: KVCacheBlock | None  # 链表指针
```

KV 块组织成链表结构，每个请求的 KV 缓存是块的单向链表。

### SingleTypeKVCacheManager

每种注意力类型有自己独立的 `SingleTypeKVCacheManager`。`KVCacheCoordinator` 管理多个 manager，根据 KV cache group 路由请求。

## 为什么需要多种 KV 缓存类型

以 DeepSeek V3 为例：
- 部分层用 FullAttention：KV 缓存是标准的 [K, V] 张量对
- 部分层用 MLA（Multi-head Latent Attention）：KV 缓存是被压缩过的 latent 表示

两种结构的 page_size_bytes 不同，必须分开管理。`KVCacheCoordinator` 为每种类型维护独立的 `SingleTypeKVCacheManager`。

## FreeKVCacheBlockQueue

空闲块队列。当 KV 缓存满时，没有空闲块 → `allocate_slots` 返回 None → 触发抢占。

## 阅读重点

- 理解 KV 块是链表结构（不是数组）
- 理解 `ref_count` 用于 prefix cache 的引用计数
- 知道「多种 KV 缓存类型」的存在
- 这些数据结构第一遍不需要深入
