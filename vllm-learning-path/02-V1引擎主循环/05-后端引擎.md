# 05 · 后端引擎：`EngineCore`（核心！）

**源码**：[`code/vllm/vllm/v1/engine/core.py`](../../code/vllm/vllm/v1/engine/core.py)

## 这是整个 vLLM 的心脏

约 600 行。`EngineCore` 拥有调度器和执行器，运行推理的紧循环。

## `__init__()` — 初始化做了什么

1. **创建 Executor**：`Executor.get_class(vllm_config)(vllm_config)` — 根据配置选 UniProc/Multiproc/Ray
2. **GPU 内存 Profiling**：
   - `executor.determine_available_memory()` 通过哑模型加载计算可用 GPU 内存
   - 可用内存 → 确定 KV 缓存能分配多少个 block
3. **初始化 KV 缓存**：`executor.initialize_from_config(kv_cache_configs)` — 分配 KV cache tensor + warmup 模型（CUDA graph 录制）
4. **创建 Scheduler**：`Scheduler(vllm_config, kv_cache_manager, ...)` — 调度器决定每步算什么
5. **设置结构化输出**：如果 `structured_outputs_config` 不为空，创建 grammar backend（XGrammar 等）
6. **冻结 Python GC**：减少 GC 暂停对延迟的影响（生产环境的微优化）

## `step()` — 推理紧循环（四个步骤）

```python
def step(self) -> dict[int, EngineCoreOutputs]:
    # 步骤 1：调度
    scheduler_output = self.scheduler.schedule()
    # → SchedulerOutput：本步要算哪些请求、各算几个 token

    # 步骤 2：执行模型前向 + 采样
    model_output = self.executor.execute_model(scheduler_output)
    # → ModelRunnerOutput（含 sampled_token_ids）

    # 步骤 3：获取语法约束（结构化输出）
    grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)
    # → 如果 model_output 中已经包含采样结果，返回 None

    # 步骤 4：更新请求状态
    engine_outputs = self.scheduler.update_from_output(
        scheduler_output, model_output
    )
    # → dict[int, EngineCoreOutputs]：本步的 token 级别输出

    return engine_outputs
```

### 步骤细节

**步骤 1 — Scheduler.schedule()**：调度器决定本步哪些请求参与计算、每个请求算几个 token。返回 `SchedulerOutput`，Executor 用它构建 GPU 输入 batch。

**步骤 2 — Executor.execute_model()**：将 `SchedulerOutput` 分发给所有 worker（每个 GPU 一个），worker 执行模型前向：
- `GPUModelRunner.execute_model()` 构建 InputBatch → 跑模型 forward → 采样 → 返回 `ModelRunnerOutput`
- 采样在 CUDA graph 录制中完成，避免 kernel launch 开销
- PP 模式：非尾 rank 返回 `IntermediateTensors` 而非 ModelRunnerOutput

**步骤 3 — Scheduler.get_grammar_bitmask()**：对使用结构化输出的请求，计算合法 token 集合（bitmask）。在步骤 2 已完成采样的场景下返回 None。

**步骤 4 — Scheduler.update_from_output()**：
1. 把新生成的 token IDs 追加到每个 Request
2. 检查 stop 条件（EOS、stop string、max_tokens）
3. 释放已完成请求的 KV 块
4. 返回 EngineCoreOutputs（前端消费）

## `step_with_batch_queue()` — Pipeline Parallelism 版本

当启用 Pipeline Parallelism（PP>1）时使用。原理是同时维护多个 in-flight batch，让调度（CPU 工作）和执行（GPU 工作）重叠：

```
时间线：
  Batch A: [调度] [GPU PP Rank0] [GPU PP Rank1] ...
  Batch B:        [调度]         [GPU PP Rank0] ...
  Batch C:                      [调度]           ...

  CPU 调度和 GPU 执行完全重叠，吞吐量近似 100% 利用率
```

## `EngineCoreProc` — 多进程版

同文件中的 `EngineCoreProc` 把 `EngineCore` 包装在独立子进程中，通过 ZMQ socket 与前端通信。它的主循环是 `run_busy_loop()`：

```python
def run_busy_loop(self):
    while True:
        # 1. 从 ZMQ socket 收新请求
        requests = self.input_socket.recv_pyobj()
        for req in requests:
            self.engine_core.add_request(req)

        # 2. 执行一步推理
        outputs = self.engine_core.step()

        # 3. 发输出给前端
        self.output_socket.send_pyobj(outputs)
```

在 DP 模式下，还有 `DPEngineCoreProc` — 在每个 GPU 上运行单独的 EngineCoreProc 实例。
