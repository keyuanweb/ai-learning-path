# 02 · 请求的内部表示

**源码**：[`code/vllm/vllm/v1/request.py`](../../code/vllm/vllm/v1/request.py)

## `Request` 类

这是请求在引擎内部的表示。调度器持有这些对象的列表，每步更新它们的状态。`Request` 是 V1 架构的基石——它把「已算多少、还剩多少」编码为两个计数器的追及关系。

## 关键字段

```python
class Request:
    request_id: str
    client_index: int           # 来自哪个前端客户端
    priority: int               # 调度优先级

    # 输入
    prompt_token_ids: list[int]
    prompt_embeds: torch.Tensor | None   # 多模态预计算 embedding
    mm_features: list[MultiModalFeatureSpec]

    # 采样配置
    sampling_params: SamplingParams | None
    pooling_params: PoolingParams | None

    # 进度跟踪（V1 核心概念！）
    num_computed_tokens: int    # 已经完成了几个 token 的 forward
    num_tokens_with_spec: int   # 总 token 数（含投机解码 draft token）

    # 状态
    status: RequestStatus
    stop_reason: int | str | None   # 触发了哪个 stop 条件

    # 输出收集
    output_token_ids: list[int]
    num_output_placeholders: int    # 投机 token 占位（等待验证）

    # Prefix caching
    block_hashes: list[BlockHash]   # 每个 KV 块的哈希值
```

## `num_computed_tokens` vs `num_tokens_with_spec` — V1 统一调度的关键

这两个字段是 vLLM V1 最核心的设计概念。V0 有显式的「prefill 阶段」和「decode 阶段」；V1 消除了这个区别。

一个请求的生命周期（以 `prompt="今天天气真好"` 为例，假设 6 个 token）：

| 阶段 | `num_computed` | `num_tokens_with_spec` | 差值 | 含义 |
|------|----------------|------------------------|------|------|
| 请求入队 | 0 | 6 | 6 | 6 个 prompt token 都待计算 |
| Chunked prefill 步1 | 4 | 6 | 2 | 算了 4 个 prompt token |
| Chunked prefill 步2 | 6 | 7 | 1 | prompt 算完，准备生成第一个 token |
| Decode 步1 | 7 | 8 | 1 | 生成第二个 token |
| Decode 步N | 106 | 107 | 1 | prompt(6) + 100 个生成 token = 106 computed, 107 即下个要生成的 |
| 投机解码 | 100 | 105 | 5 | draft model 预测了 5 个 draft token |

**关键洞察**：调度器不需要区分 prefill/chunked prefill/decode/speculative —— 它们都只是「让 `num_computed_tokens` 追上 `num_tokens_with_spec`」的不同速度。

## `RequestStatus`

```python
class RequestStatus(Enum):
    WAITING = 0                        # 在等待队列中
    RUNNING = 1                        # 被调度器持有
    FINISHED_STOPPED = 2               # EOS 结束
    FINISHED_LENGTH_CAPPED = 3         # 达到 max_tokens
    FINISHED_ABORTED = 4               # 被取消
    FINISHED_IGNORED = 5               # 被忽略（如多余的 n>1 completion）
    FINISHED_PREEMPTED_WITH_ERROR = 6  # 因错误被抢占
```

状态迁移：`WAITING → RUNNING → FINISHED_*`，唯一例外是 RUNNING 请求可能退回到 WAITING（抢占）。
