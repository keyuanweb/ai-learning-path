# 02 · 请求的内部表示

**源码**：[`code/vllm/vllm/v1/request.py`](../../code/vllm/vllm/v1/request.py)

## `Request` 类

这是请求在引擎内部的表示。调度器持有这些对象的列表，每步更新它们的状态。

## 关键字段

```python
class Request:
    request_id: str
    client_index: int
    priority: int

    # 输入
    prompt_token_ids: list[int]
    prompt_embeds: torch.Tensor | None
    mm_features: list[MultiModalFeatureSpec]

    # 采样配置
    sampling_params: SamplingParams | None
    pooling_params: PoolingParams | None

    # 进度跟踪（核心概念！）
    num_computed_tokens: int     # 已经算了几步
    num_tokens: int              # 总共有几个 token（含投机 token）

    # 状态
    status: RequestStatus

    # 输出
    output_token_ids: list[int]
    num_output_placeholders: int  # 投机 token 占位

    # Prefix caching
    block_hashes: list[BlockHash]
```

## `num_computed_tokens` vs `num_tokens` — 理解 V1 统一调度的关键

这是 vLLM V1 最核心的设计概念。一个请求：

- 开始：`num_computed_tokens = 0`, `num_tokens = len(prompt_token_ids)`
- 调度器每步算一些 token，`num_computed_tokens` 向 `num_tokens` 追近
- 追上时 prompt 已全部处理完，开始逐 token decode：`num_computed_tokens = N`, `num_tokens = N+1`
- 投机解码时 `num_tokens` 可能比 `num_computed_tokens` 大很多

这个设计统一了 prefill、chunked prefill、decode、speculative decoding —— 它们都只是「追」的不同速度。

## `RequestStatus`

```python
class RequestStatus(Enum):
    WAITING = 0
    RUNNING = 1
    FINISHED_STOPPED = 2
    FINISHED_LENGTH_CAPPED = 3
    FINISHED_ABORTED = 4
    ERROR = 5
```

状态迁移：`WAITING → RUNNING → FINISHED_*`

## 阅读重点

- 彻底理解 `num_computed_tokens` 和 `num_tokens` 的语义
- 记住请求的状态机
- 知道 `block_hashes` 的存在（用于 prefix caching）
