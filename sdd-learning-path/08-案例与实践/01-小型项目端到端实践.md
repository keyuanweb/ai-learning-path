# 小型项目端到端实践

本章以一个完整的 Todo CLI 工具为例，从零开始走通 SDD 七步工作流——Constitution → Specify → Clarify → Plan → Tasks → Implement → Verify。

---

## 1. 项目背景

**Todo CLI**：一个命令行任务管理工具，支持添加、列表、完成、删除任务，数据持久化到本地 JSON 文件。

选择这个项目的原因是：
- 功能边界清晰，适合一次完整的 SDD 流程演示
- 不涉及外部依赖、数据库、网络通信——关注点全在规范和方法论上
- 任何人都能理解需求，不需要领域知识

---

## 2. Constitution（项目宪法）

### 输入给 AI 的 prompt：

```
/speckit.constitution Todo CLI 是一个命令行任务管理工具。
使用 Python 3.13，不依赖第三方库（只用标准库）。
代码必须包含 Type Hints 和 Docstring。
所有函数必须有对应的 pytest 测试（覆盖率 > 80%）。
CLI 参数解析使用 argparse。
数据存储使用本地 JSON 文件。
错误信息必须清晰、用户友好。
```

### AI 生成的 constitution.md 关键内容：

```markdown
# Todo CLI Constitution v1.0.0

## 核心原则

### 原则 1：标准库优先
- 禁止引入任何第三方依赖（pip install 不应被需要）
- 所有功能使用 Python 标准库实现

### 原则 2：可测试性
- 每个公开函数必须有对应的单元测试
- 测试覆盖率不低于 80%
- 数据读写逻辑与 CLI 展示逻辑分离（可独立测试）

### 原则 3：用户体验
- 所有错误信息包含"发生了什么"和"用户该怎么做"
- 命令输出格式统一（成功/失败有明确区分）
- 交互式操作前必须确认（如删除）

### 原则 4：数据完整性
- JSON 文件读写使用原子操作（先写临时文件再 rename）
- 启动时自动检测数据文件完整性
- 异常情况下不丢失数据
```

## 3. Specify（编写规范）

### 输入给 AI 的 prompt：

```
/speckit.specify 开发 Todo CLI，功能包括：
1. 添加任务：todo add "Buy groceries"
2. 列出任务：todo list（显示序号、状态、内容）
3. 完成任务：todo done 1（标记序号1的任务为完成）
4. 删除任务：todo delete 1（删除序号1的任务，需确认）
5. 数据持久化到 ~/.todo.json

约束：
- 已完成任务与未完成任务在列表中用不同颜色/标记区分
- 任务序号从 1 开始
- 删除前提示确认 y/N
```

### AI 生成的功能规范（spec.md）关键部分：

```markdown
# Spec: Todo CLI v1.0

## 用户故事

### US-1: 添加任务
As a 用户
I want to 用命令行添加新任务
So that 我能快速记录待办事项

验收条件：
- Given 用户执行 `todo add "Buy groceries"`
- When 任务列表为空
- Then 新增一条内容为 "Buy groceries" 的未完成任务
- And 终端输出 "✓ 已添加任务 #1: Buy groceries"

### US-2: 列出任务
As a 用户
I want to 查看所有任务的列表
So that 我能了解当前待办事项的状态

验收条件：
- Given 存在 2 个未完成任务和 1 个已完成任务
- When 用户执行 `todo list`
- Then 输出格式：
  [1] ⬜ Buy groceries
  [2] ✅ Call dentist
  [3] ⬜ Write report

### US-3: 完成任务
...

### US-4: 删除任务
...

## 异常场景

### EX-1: 空任务列表
- When 执行 `todo list` 且任务列表为空
- Then 输出 "暂无任务。使用 'todo add' 添加第一个任务。"

### EX-2: 无效的任务序号
- When 执行 `todo done 999` 且任务不存在
- Then 输出 "✗ 错误：任务 #999 不存在。使用 'todo list' 查看所有任务。"

### EX-3: 数据文件损坏
- When JSON 文件格式错误
- Then 输出 "✗ 错误：数据文件损坏。已备份到 ~/.todo.json.bak"
```

## 4. Clarify（澄清）

### AI 提出的澄清问题（示例）：

```
Q1: 任务内容是否允许为空字符串？
A1: 不允许。todo add "" 应提示 "✗ 任务内容不能为空"

Q2: 已完成任务能否被删除？
A2: 可以。已完成任务和未完成任务都可以删除。

Q3: 是否需要支持编辑任务内容？
A3: V1 不支持。编辑功能留到 V2。

Q4: 多个终端同时操作时如何处理？
A4: V1 不做并发控制。每次读写 JSON 使用原子操作即可。
```

澄清后的关键补充：
- 输入验证规则（任务内容必填、长度限制 500 字符）
- V1 明确的功能边界（哪些不做）
- 异常场景补充（无权限写入文件、磁盘空间不足）

## 5. Plan（实施计划）

AI 生成的技术计划：

```markdown
# Plan: Todo CLI v1.0

## 架构设计

```
CLI 层 (argparse) → Service 层 (业务逻辑) → Storage 层 (JSON 文件)
```

## 模块划分

| 模块 | 文件 | 职责 |
|------|------|------|
| CLI | cli.py | 参数解析、命令分发 |
| Service | service.py | 任务 CRUD、输入验证 |
| Storage | storage.py | JSON 读写、原子操作 |
| Models | models.py | Task 数据类定义 |

## 数据模型

```python
@dataclass
class Task:
    id: int
    content: str
    done: bool = False
    created_at: str = ""
```

## 技术决策
- 数据文件路径：~/todo.json（Unix）/ %USERPROFILE%\todo.json（Windows）
- 原子写入策略：tempfile + os.replace
- 命令实现模式：每个命令一个独立函数
```

## 6. Tasks（任务分解）

AI 将 Plan 分解为可执行任务：

```
Task 1: 创建项目结构和 Task 数据模型
Task 2: 实现 Storage 层（JSON 读写）
Task 3: 实现 Service 层（任务 CRUD）
Task 4: 实现 CLI 层（参数解析 + 命令分发）
Task 5: 编写集成测试
Task 6: 编写 README 和安装说明
```

每个任务包含：
- 关联的 Spec 章节
- 验收条件
- 依赖关系（Task 3 依赖 Task 2，Task 4 依赖 Task 3 等）
- 预估工作量（0.5-2h）

## 7. Implement（实现）

按 Task 1→6 顺序执行，每个 Task 的实现对照规范：

**Task 2 实现示例**（Storage 层 —— 对照规范 §原子写入）：

```python
# storage.py
# @spec: SPEC-001 §5 — 数据持久化到 ~/.todo.json
# @spec: SPEC-001 §EX-3 — 数据文件损坏处理
import json
import os
import tempfile
from pathlib import Path
from typing import List
from models import Task

DATA_FILE = Path.home() / ".todo.json"
BACKUP_FILE = Path.home() / ".todo.json.bak"

def load_tasks() -> List[Task]:
    """从 JSON 文件加载任务列表。"""
    if not DATA_FILE.exists():
        return []
    try:
        with open(DATA_FILE, "r") as f:
            data = json.load(f)
        return [Task(**item) for item in data]
    except (json.JSONDecodeError, KeyError) as e:
        DATA_FILE.rename(BACKUP_FILE)
        raise RuntimeError(
            f"数据文件损坏，已备份到 {BACKUP_FILE}\n"
            "原有的损坏文件已备份，已创建新的空任务列表。"
        )

def save_tasks(tasks: List[Task]) -> None:
    """原子写入任务列表到 JSON 文件。"""
    data = [{"id": t.id, "content": t.content,
             "done": t.done, "created_at": t.created_at}
            for t in tasks]
    with tempfile.NamedTemporaryFile(
        mode="w", dir=DATA_FILE.parent,
        delete=False, suffix=".tmp"
    ) as tmp:
        json.dump(data, tmp, indent=2, ensure_ascii=False)
    os.replace(tmp.name, DATA_FILE)
```

### 实现过程中的关键决策记录：

```
Task 2 实现时发现：规范中没有定义任务 ID 的生成策略。
→ 回查 Clarify 记录：无相关说明。
→ 补充决策：使用自增整数（max_id + 1），记录在 ADR 中。
→ 更新 Spec：在数据模型部分添加 ID 生成规则。
```

> 这是 SDD 的核心循环——实现中发现规范不完整，回到规范修改，而非在代码中偷偷决定。

## 9. 经验总结

### 这个案例教给我们的：

1. **规范在前，代码在后**：30 分钟写规范 = 节省 3 小时返工
2. **澄清环节不可跳过**：输入验证、并发、功能边界——这些如果到编码时才发现，成本翻 10 倍
3. **实现中发现的问题要回到规范**：不要偷偷决定，更新 Spec 让所有人（包括未来的自己）知道
4. **验证对照清单是最佳实践**：逐条打勾的感觉比"差不多做完了"可靠得多
5. **Constitution 的约束是全流程的**：比如"标准库优先"这条原则影响了所有技术决策

### 从 Todo CLI 到真实项目：

| Todo CLI 的做法 | 真实项目的对应 |
|----------------|---------------|
| 单人、单模块 | 多人、多模块（需要接口规范前置） |
| JSON 文件存储 | 数据库、缓存、消息队列（需要数据契约） |
| 手动执行验证 | CI 自动化验证（规范合规检查跑在 pipeline 里） |
| 心智模型中的依赖 | 显式的任务依赖 DAG |
| 一次性写完 | 迭代式 SDD（每周/每 Sprint 一个 Spec 增量） |
