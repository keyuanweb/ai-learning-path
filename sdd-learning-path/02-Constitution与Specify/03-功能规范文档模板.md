# 功能规范文档模板

## 1. 模板设计原则

功能规范文档（Feature Specification）是 SDD 工作流中 Specification 阶段的核心交付物。一个好的模板需要满足以下设计原则：

| 原则 | 说明 |
|------|------|
| **简洁够用** | 只包含必要字段，不引入过度设计。一个新人能在 10 分钟内理解模板结构并开始填写 |
| **可扩展** | 字段可增可减。简单功能用简化版，复杂功能加自定义章节——模板不强制任何字段必填 |
| **AI 可解析** | 结构化程度足够高，LLM 能准确提取验收条件、异常场景等关键信息，用于后续的 Plan/Implement/Verify 阶段 |
| **人类可审查** | 非技术人员（产品经理、QA）也能看懂并参与评审。避免纯代码描述，用户故事和验收条件用自然语言 |

## 3. 完整示例：用户注册功能

以下是一个真实可用的完整规范，可作为填写参考。

````markdown
# 功能规范：用户注册

## 规范元信息

| 字段 | 值 |
|------|-----|
| 规范编号 | SPEC-USER-001 |
| 标题 | 用户注册功能：通过邮箱验证码完成账号注册 |
| 状态 | 评审中 |
| 版本 | v1.0 |
| 作者 | AI 工程师 |
| 日期 | 2026-08-11 |

---

## 背景与问题描述

### 当前现状
当前系统无自建用户体系，依赖第三方 OAuth 登录（仅支持 Google）。部分目标用户（企业内网环境）无法使用 Google 登录。

### 期望目标
提供邮箱+密码的注册方式，用户通过邮箱验证码激活账号后即可登录。支持用户名唯一标识，便于社区功能中 @提及。

### 范围界定
- **包含**：邮箱注册、验证码发送与校验、密码强度校验、用户名唯一性校验
- **不包含**：手机号注册、第三方 OAuth 绑定已有账号（SPEC-AUTH-002）、邀请注册机制

---

## 用户故事

### US-01：新用户邮箱注册
> As a 新访客，I want 使用邮箱和密码创建账号，So that 我能够在平台保存个人数据和参与社区互动

### US-02：邮箱验证
> As a 注册中的用户，I want 收到并输入邮箱验证码，So that 我的账号被激活且系统确认我是邮箱所有者

---

## 验收条件

### AC-01：正常注册流程
- **Given** 用户访问注册页面，尚未注册过
- **When** 用户填写用户名"alice"、邮箱"alice@example.com"、密码"SecurePass123!"，点击"发送验证码"，输入收到的验证码，点击"注册"
- **Then** 账号创建成功，返回 201 和用户基本信息（不含密码），自动跳转至登录后首页

### AC-02：邮箱已存在
- **Given** 邮箱"alice@example.com"已被注册
- **When** 用户使用相同邮箱发起注册
- **Then** 返回 409，消息"该邮箱已被注册"，不发送验证码

### AC-03：密码强度不足
- **Given** 用户填写了有效邮箱和用户名
- **When** 用户输入密码"123456"（不满足强度要求）
- **Then** 返回 422，消息"密码需包含至少 8 位字符，含大写字母、小写字母和数字"

### AC-04：验证码错误或过期
- **Given** 用户已请求发送验证码，但输入了错误验证码或验证码已过期（超过 5 分钟）
- **When** 用户提交注册
- **Then** 返回 400，消息"验证码错误或已过期"，允许用户重新获取验证码

### AC-05：用户名重复
- **Given** 用户名"alice"已被占用
- **When** 用户提交注册
- **Then** 返回 409，消息"该用户名已被使用"，不消耗验证码状态（用户可修改用户名后重试）

---

## 功能描述

### 核心流程

```
客户端 -> POST /api/users/register {username, email, password} -> 服务端
服务端 -> 校验输入 -> 校验通过
服务端 -> 生成验证码，存储（TTL=5min）-> 发送邮件
服务端 -> 返回 202 {message: "验证码已发送"}
客户端 -> POST /api/users/register/verify {email, code} -> 服务端
服务端 -> 校验验证码 -> 创建用户（bcrypt(password)）-> 返回 201 {user}
```

### API 端点

#### POST /api/users/register
请求用户注册，发送验证码。

**Request:**
```json
{
  "username": "alice",
  "email": "alice@example.com",
  "password": "SecurePass123!"
}
```

**字段规范：**

| 参数 | 类型 | 必填 | 校验规则 |
|------|------|------|----------|
| username | string | 是 | 3-30 字符，字母数字及下划线，首字符必须为字母 |
| email | string | 是 | 合法邮箱格式，最大 255 字符 |
| password | string | 是 | 8-128 字符，必须含大写、小写、数字 |

**Response 202（验证码已发送）:**
```json
{
  "code": 202,
  "message": "验证码已发送至邮箱，5分钟内有效",
  "data": {
    "email": "alice@example.com",
    "expires_in_seconds": 300
  }
}
```

**Response 409（邮箱或用户名已存在）:**
```json
{
  "code": 409,
  "message": "该邮箱已被注册",
  "detail": null
}
```

**Response 422（校验失败）:**
```json
{
  "code": 422,
  "message": "输入校验失败",
  "errors": [
    {"field": "password", "message": "密码需包含至少 8 位字符，含大写字母、小写字母和数字"}
  ]
}
```

#### POST /api/users/register/verify
提交验证码，完成注册。

**Request:**
```json
{
  "email": "alice@example.com",
  "code": "123456"
}
```

**Response 201（注册成功）:**
```json
{
  "code": 201,
  "message": "注册成功",
  "data": {
    "id": "u_abc123",
    "username": "alice",
    "email": "alice@example.com",
    "created_at": "2026-08-11T10:30:00Z"
  }
}
```

**Response 400（验证码错误或过期）:**
```json
{
  "code": 400,
  "message": "验证码错误或已过期",
  "detail": null
}
```

### 数据模型

**users 表（注册相关字段）：**

| 字段 | 类型 | 约束 |
|------|------|------|
| id | varchar(32) | PK, 雪花ID |
| username | varchar(30) | UNIQUE, NOT NULL |
| email | varchar(255) | UNIQUE, NOT NULL |
| password_hash | varchar(255) | NOT NULL, bcrypt($2b$12$) |
| status | enum('pending','active','disabled') | NOT NULL, DEFAULT 'pending' |
| email_verified_at | timestamp | NULL, 验证码校验成功后写入 |
| created_at | timestamp | NOT NULL |

**verification_codes 表（Redis，非持久化）：**

| Key 模式 | TTL | 说明 |
|----------|-----|------|
| `reg:code:{email}` | 300s | 6 位数字验证码 |
| `reg:attempts:{email}` | 900s | 尝试次数计数，24h 内最多 5 次 |
| `reg:pending:{email}` | 300s | 暂存的注册信息（username, password_hash） |

## 边界条件与异常处理

### EX-01：邮箱已存在
- **触发条件**：POST /api/users/register 时，email 已存在于 users 表中且 status 为 active
- **系统行为**：不发送验证码，返回 409
- **用户感知**：提示"该邮箱已被注册，请直接登录或使用其他邮箱"

### EX-02：用户名已存在
- **触发条件**：POST /api/users/register/verify 时，username 已存在
- **系统行为**：不创建用户，不消耗验证码，返回 409
- **用户感知**：提示用户名已被使用，可修改后重新提交验证

### EX-03：验证码发送频率限制
- **触发条件**：同一 IP 或同一邮箱在 60 秒内重复请求发送验证码
- **系统行为**：返回 429 Too Many Requests，Retry-After 头部指示剩余等待秒数
- **用户感知**：提示"发送过于频繁，请 30 秒后再试"

### EX-04：邮件发送失败
- **触发条件**：邮件服务不可用或发送超时（超过 3 秒）
- **系统行为**：返回 502，不扣除发送配额，建议用户重试
- **用户感知**：提示"验证码发送失败，请稍后重试"

### EX-05：24 小时内验证码请求次数超限
- **触发条件**：同一邮箱 24 小时内请求验证码超过 5 次
- **系统行为**：返回 429，冻结该邮箱 24 小时
- **用户感知**：提示"今日验证码请求次数已达上限，请 24 小时后再试"

### EX-06：必填字段缺失
- **触发条件**：请求体中缺少 username、email 或 password 任一字段
- **系统行为**：返回 422，errors 数组明确列出缺失字段
- **用户感知**：表单字段标红，提示哪些信息必填

### EX-07：邮箱格式错误
- **触发条件**：email 字段不符合 RFC 5322 基本格式
- **系统行为**：返回 422，在 errors 数组中明确指出 email 格式问题
- **用户感知**：邮箱输入框标红，提示"请输入有效的邮箱地址"

---

## 非功能需求

### 性能
- **P95 响应时间**：POST /api/users/register < 500ms（不含邮件发送耗时）
- **P99 响应时间**：POST /api/users/register/verify < 300ms
- **并发支持**：注册接口支持 200 QPS（初版估算）

### 安全
- **密码存储**：使用 bcrypt 哈希，cost factor = 12（`$2b$12$`）
- **验证码安全**：6 位随机数字，5 分钟过期，验证次数限 5 次
- **防暴力破解**：同一邮箱 24 小时内最多 5 次验证码请求；同一 IP 每秒最多 3 次注册请求
- **敏感信息**：日志中不记录密码明文和完整验证码（仅记录后 2 位用于排查）

### 可用性
- **邮件服务降级**：主邮件服务不可用时，自动切换至备用邮件服务；双备均不可用时返回明确错误，不静默失败
- **幂等性**：重复提交相同已验证的验证码返回 200（而非 409），提示"该邮箱已完成注册"
````

## 4. 模板使用建议

### 4.1 不要僵化

模板的字段不是法律，而是工具箱。核心原则是：**写清楚"要做什么"和"怎么算做完"，其他都是辅助。**

- 纯内部工具、无用户可见变更 → 可省略用户故事
- 性能要求不敏感的内部批处理任务 → 可省略非功能需求
- 单人独立开发的脚本 → 可省略依赖与前置条件

### 4.2 按功能规模选用

| 功能规模 | 建议模板 | 核心内容 |
|----------|----------|----------|
| 1-2 天（小） | 简化版 | 用户故事 + 验收条件（3-5 条）+ 异常场景（2-3 个） |
| 3-5 天（中） | 完整版去除非必要章节 | 简化版 + 功能描述 + 数据模型 + 非功能约束 |
| 1-2 周（大） | 完整版 | 所有章节，额外补充安全评审和架构评审节点 |
| 跨迭代（超大） | 拆分为多个子规范 | 每个子规范独立使用完整版，主规范仅描述拆解和接口契约 |

### 4.3 规范写完后必答的 5 个问题

规范写完后，在提交评审前，逐条自查以下清单。无法回答的问题意味着规范有遗漏：

1. **"一个新人读完能否直接开始编码？"** —— 如果还需要大量口头沟通补充细节，规范不合格
2. **"所有异常路径都覆盖了吗？"** —— 输入为空、输入超长、并发冲突、依赖挂了……至少列出 5 个异常场景
3. **"验收条件可以被自动化测试吗？"** —— 每条 AC 的 Given-When-Then 应该能直接翻译为测试用例
4. **"边界值明确吗？"** —— "大量数据"是多少条？"快速响应"是几百毫秒？数字必须出现
5. **"'不做什么'写清楚了吗？"** —— 如果没有范围界定，评审时一定会被追问"那 XXX 要不要顺便做？"

### 4.4 协作流程建议

```
[作者] 填写规范 -> [自检] 五问清单 -> [提交] 规范评审
    -> [评审人] 基于规范提出场景遗漏和建议 -> [作者] 修订 -> [批准]
    -> [开发者] 基于规范编写实现计划 -> [QA] 基于验收条件编写测试用例
```

规范的评审者最好是 **产品经理 + 开发者 + QA** 三者都有代表参与，各自关注不同维度：

- 产品经理：用户故事和验收条件是否对齐需求
- 开发者：技术边界和异常场景是否可落地
- QA：验收条件是否可测量、可自动化

## 5. 小结

一份好的功能规范文档，不在于用了多少字段、写了多少页，而在于三件事：

1. **对齐预期** —— 让产品、开发、测试三方对"做完是什么样"有完全一致的画面
2. **边界清晰** —— 知道什么该做、什么不该做，异常情况如何处理
3. **可被验证** —— 验收条件能直接翻译为测试用例，not just a wish list

SDD 工作流中，Specify 阶段的产出物就是这份规范。后续的 Plan（实现计划）和 Tasks（任务拆解）都以此为唯一事实来源。规范写得好，后面三个阶段会顺滑得多；规范有坑，后面步步踩坑。
